# smb-CRM на форке Twenty: цель, принципы и план (v3, 2026-10-09)

**Источник:** входной документ владельца от 2026-10-09 (`pasted_content_2026-10-09_12-23-22-364_a01405.txt`).
Роль читателя: исполнитель (Hermes/агенты) и владелец. Язык общения: русский. Промпты агентам: подробные, с конкретными примерами и командами, без формулировок «сделай как надо». Ориентир: качество, стандарты, стабильность, современный стек, никаких костылей.

## 1. Цель

Production-уровень CRM для малого и среднего бизнеса, конкурент Битрикс24, на форке Twenty (тег twenty/v2.45.6, коммит 6007ad5a7f). Одновременно ответвление-канал: приложение в Битрикс24 с авторизацией через портал клиента, встраиванием в интерфейс Б24 и единым доменом.

Решение владельца (зафиксировано): делаем полную CRM сразу, Б24-приложение это канал в неё, а не отдельный продукт и не первый этап.

Развёртывание: один сервер, 5 клиентов, у каждого свой сабдомен и свой workspace, примерно по 50 пользователей (≈250 всего). Размер сервера подбираем после нагрузочного замера, не заранее.

Функциональность:
- визуальный слой: бренд, обои, акцент, на токенах `--t-*`;
- «Задачи 2.0»: обязательные и необязательные поля по статусам, чат внутри задачи;
- беседы и мессенджер (нативно, мост Mattermost только как опция позже);
- процессы по модулям (аналог бизнес-процессов Б24): workflow + человеческие шаги на задачах;
- модули включаются по workspace (пресеты); клиент может править модуль или писать свой;
- канал Б24: установка, вход, встраивание (раздел 6);
- позже: документооборот, Gantt, отчёты, HR, омниканальность (вне горизонта ближайшего года).

## 3. Архитектурные решения (рекомендации, статус)

Утверждать СЕЙЧАС только направление:
- ADR-001: гибрид, Apps по умолчанию, швы по реестру.
- ADR-005: токены, затем швы.
- ADR-006a: пресеты как наборы Apps, свой реестр дистрибуции.
Не утверждать, пока нет спайков: ADR-002 (S2 и права чата), ADR-003 (S4), ADR-004 (S3), ADR-007 (stub-хук и цена шва).
Не реализовывать вообще до юриста: ADR-006b (лицензия, лимиты, свой Enterprise-ключ).

Единый шов (ADR-007): ровно один импорт серверного слоя и одна точка входа фронта; ID P-002 и P-003 зарезервированы за ними (служебные записи P-010+). Способ размещения кода форка (пакеты packages/smb-* = M1 или каталоги packages/twenty-*/src/smb = M2) выбирается ОДНИМ решением для сервера, фронта и скина по измерению (git diff --stat двух макетов, проверка цикла импортов, список затронутых существующих файлов).

## 4. Стек и принципы разработки

Стек: Nx/Yarn 4 monorepo, NestJS, React 18, PostgreSQL (схема workspace_<id> на workspace + core), Redis, BullMQ, GraphQL + SSE, Node ^24.5.0. Деплой: образ собирается в CI (linux/amd64) → GHCR → SSH forced command → staging/prod, один образ на оба, различаются .env и тома.

Принципы:
1. Сначала вопрос «штатно?» (Apps, feature-flag, validationRule, page-layout tab, FRONT_COMPONENT, hook).
2. Наш код только в наших каталогах; правка файла из upstream = запись в PATCHES.md; больше одной строки = ADR. Гейт нельзя ослаблять без ревью владельца (CODEOWNERS + проверка версией скрипта из main).
3. Избегать горячих зон upstream (generated-metadata, application, page-layout, workflow); швы предпочтительно в зонах с малым churn (query-hook, task, роутинг).
4. House rules Twenty: комментарии только про WHY, types вместо interfaces, без any, именованные экспорты, Lingui для строк, Linaria для стилей, иконки из twenty-ui, не переизобретать guards.
5. Правдивость: «проходит» только с выводом запущенной команды; иначе NOT RUN и причина. Каждый факт = путь:строка на базе v2.45.6 + вывод. Документация (.mdx) доказательством поведения не считается.
6. Миграции только expand → backfill → contract. Откат образа после upgrade ядра безопасен только с restore из дампа.
7. Применять к коду форка выборочно инварианты blueprint: идемпотентность команд, побочные эффекты после COMMIT, SafeFetcher для внешних запросов, HMAC+timestamp+nonce для вебхуков, append-only журналы с причиной, отсутствие обхода прав. Не применять: outbox→Kafka, «ноль DDL в рантайме», PDP по gRPC, closure-таблицы (чужая архитектура).
8. Не коммитить locales/*.po и locales/generated/*, секреты, .env. Не писать AI-атрибуцию в коммиты.
9. Тяжёлые команды (gitleaks по истории, docker build, nx build, jest целиком, Playwright, filter-branch): только с согласия владельца, nice -n 19, GOMAXPROCS=2 / --jobs 2, и не при swap > 80%.
10. Проверки после задачи: tsgo --noEmit в затронутом пакете (не nx typecheck: кэш), lint:diff-with-main, точечный jest/vitest на новое поведение; интеграционные тесты отдельным этапом на VM.

## 5. Безопасность, обязательная для всего

- Нет обхода прав (аналог disableCheckAccess), нет SQL-конкатенации, нет eval.
- Секреты: .secrets вне репозитория, отдельные ключи staging/prod, ENCRYPTION_KEY бэкапить отдельно от дампов.
- Деплой: forced command с жёсткой регуляркой (тег не начинается с «-», вызов после «--»), два SSH-ключа (prod-ключ только в Environment production), агентам боевые ключи не выдавать.
- Репозиторий приватный до пуша; ветки backup/* не пушить; пуш в ветку, не в main.

## 6. Канал Битрикс24 (ответвление CRM)

Цель: клиент ставит приложение из маркетплейса или локально; портал получает workspace на своём сабдомене единого домена; сотрудник Б24 входит без пароля; CRM открывается внутри Б24 в iframe.

Модель: ОДИН инстанс Twenty, мультиарендность по сабдоменам (штатно), wildcard-сертификат на *.домен. Вопрос владельцу: зачем отдельный тоннель на клиента? Рекомендация: если порты не должны торчать наружу, достаточно одного фронтового прокси (Caddy, wildcard DNS-01); тоннель на клиента добавляет сложность без выгоды в этой модели.

Требования безопасности (из S6; формулировки по документации Б24 проверять по URL):
- Идентичность пользователя = (portal member_id, b24_user_id), не email. Автослияния аккаунтов по email нет.
- Первый install: доказательство владения порталом обратным REST-вызовом (assertPortalClaim) ТОЛЬКО на домены из белого списка Битрикс24; произвольный domain из тела запроса запрещён (угроза фальшивого портала и SSRF).
- uninstall: сверка application_token, 403 без частичной обработки, идемпотентность, судьба данных заранее решена.
- Идемпотентный install (повтор не создаёт второй workspace), rate-limit, журнал причин.
- Токены Б24 только шифрованными (enc:v2).
- Редирект на сабдомен: regex метки ^[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?$, new URL(), сравнение host с ${slug}.${frontDomain}, слаг из ответа вашего API (закрывает H1).
- frame-ancestors формируется динамически по подтверждённому домену портала клиента, не глобальным списком.
- Вход в iframe не должен зависеть от сторонних cookie (Safari/Firefox/мобильный WebView): токен через postMessage с короткоживущей сессией. Проверяется экспериментом E1.
- Поддержка: v1 только облачные порталы Б24; коробочные с произвольным доменом отдельным решением владельца.
- DNS_ROOT_DOMAIN конфигурируется через env, дефолта нет (fail-closed), хардкод crm-systems-ai.ru убрать.

Код старого контура company-tunnel переиспользуется ТОЛЬКО после: ревизии по этому списку, запуска его тестов на VM, переноса на v2.45.6 и typecheck. Копирование вслепую запрещено.

Каждый следующий шаг стартует только если закрыт гейт предыдущего.

Этап 0. Решения владельца и безопасность (без кода)

  0.2 Пуш ветки chore/docs-and-tooling (не main). Затем Settings → Branches: обязательный PR + обязательные проверки (check-core-patches, typecheck, lint, unit, integration, docker).
  0.3 Юристу (не заключение, а вопросы): AGPL §13 и производность smb-* кода; правка констант лимитов и «свой ключ»; хранение/запуск 475 Enterprise-файлов в образе; публикация аудита Б24 и права на обои/логотип; товарный знак при ребрендинге; персональные данные РФ и место хостинга (152-ФЗ); лицензии зависимостей (SBOM).
  0.4 Взять Linux-VM. Логотип клиента: исходник и права от владельца бренда. BRAND.md с палитрой: пока TEMP.

Этап 0.5. Спайки и закрытие дыр (до любых модулей), на VM
  A2: перепроверка слабых «VERIFIED» (уведомления, все call-sites лимитов, сигнатура декоратора хука, язык выражений validationRule, answerToolCall из logic function, вкладка на стандартную карточку task), цена шва M1/M2, stub-хук task.updateOne из стороннего пакета, вшить «Поправки» в тела ADR.
  S1 Hello module (install/uninstall/upgrade на чистом workspace). S3 обязательность по статусу (доставка правил без ключа в манифесте, UX отказа на канбане/inline). S4 пробуждение процесса из logic function. S2 чат-виджет в Remote DOM (кириллица с IME, @упоминания, длинные списки, SSE). S5 лимиты и Enterprise-зоны (воспроизвести 5/25).
  S6-эксперименты E1–E5 на тестовом портале Б24 (iframe и cookie, frame-ancestors, install и идемпотентность, привязка по (portal, user), uninstall).
  Деплой D2 параллельно, без боевых секретов: bats и shellcheck для forced command, два ключа, HEALTH_TIMEOUT и запрет автоотката при идущем upgrade, mem_limit, проверочный restore с замером RTO на тестовых данных, offsite, SBOM, staging на отдельном поддомене.
  Нагрузочный замер: 5 workspace × 50 пользователей на VM (память процессов, размер метаданного кэша, время старта).
  По нему подбирается сервер.
  Гейт: утвердить ADR-002/003/004/007 по результатам; зафиксировать M1/M2.

Этап 1. Каркас швов: единый серверный шов и точка входа фронта (P-002, P-003), project.json, workspaces, Dockerfile COPY, allowlist гейта, dev-стек зелёный.
Этап 2. Визуал: токены (packages/smb-brand, проверки токенов и контраста в CI), затем скин (обои, акцент, стекло) из архива старого форка с минимумом швов (цель: один). Подмена скелетонов без правок ядра по умолчанию.
Этап 3. Задачи 2.0: поля, правила обязательности по статусам (механизм доставки по S3), вью «Просроченные», контрактный тест validationRule против изменений upstream.
Этап 4. Беседы в записи (ветка по результату S2): модель, права (матрица ролей на реальных запросах), уведомления (источник событий и дедупликация), unread, производительность на 10 000 задач.
Этап 5. Процессы: шаблон «Согласование» (workflow + задача), идемпотентное возобновление, остановка при удалении задачи, SLA-уведомления, ограничения записать (нет отката, нет делегирования).

Этап 7. Упаковка модулей и пресетов: один макет (одно приложение с флагами или несколько без кросс-ссылок), команды yarn smb:preset install/uninstall, свой реестр (APP_REGISTRY_URL + tarball), руководство автора модуля.
Этап 8. Документооборот (референс: старый doc-management, перепись на штатный путь), затем отчёты, Gantt, HR.
Этап 9. Омниканальность: вне горизонта ближайшего года.

## 8. Определение «готово» для любой задачи

1. Код в наших каталогах, либо запись в PATCHES.md (+ADR при больше одной строки).
2. tsgo и lint:diff-with-main выполнены фактически, вывод приложен.
3. Тест на новое поведение написан и прогнан, иначе NOT RUN с причиной.
4. House rules соблюдены; Docker, workspaces и Nx обновлены, если добавлялся пакет.
5. Шов не расширен сверх allowlist; гейт и bats зелёные.
6. Отчёт docs/reports/<id>.md: Сделано / Подтверждено (команда + вывод) / NOT RUN / Расхождения с ADR / Вопросы владельцу.
