# ADR-013: Серверный фундамент форка — место шва, свои таблицы, установка модулей в компанию

**Статус:** п.1 и п.2 реализованы и проверены прогоном 2026-10-12 (отчёт R07 (история git)); п.3–п.5 — предложено. Утверждение за владельцем.
**Дата:** 2026-10-12
**Основание:** ревизия сделанного по ADR-009/010 (M-1, M-4, M-7, N-1) против кода базы `twenty/v2.45.6`
**Связанные:** [ADR-007](ADR-007-unified-stitch.md), [ADR-008](ADR-008-instance-topology-b24-gateway.md), [ADR-009](ADR-009-module-contract.md), [ADR-010](ADR-010-communications.md)
**Исправляет:** ADR-009 п.4 (место P-002) и «Что нужно проверить» №4 (свои таблицы через instance-команды); ADR-010 п.2 и п.6 (где лежат таблицы бесед и уведомлений)

---

## Контекст

Ревизия нашла три дефекта основания, на котором стоят все будущие модули. Каждый воспроизводится чтением кода базы; два первых подтверждены запуском.

### Дефект 1. Шов P-002 стоял в дереве, которое грузит только сервер

P-002 был в `src/modules/modules.module.ts`. `ModulesModule` импортируется только в `app.module.ts:61`.

- **Воркер его не грузит:** `queue-worker.module.ts:11` импортирует `CoreEngineModule` и `JobsModule`. Значит, в воркере не было ни одного нашего провайдера: PRE-хук «нельзя закрыть задачу без обязательных полей» не срабатывал бы на изменениях записей, которые делает сам процесс (шаг workflow «обновить запись» исполняется в воркере), а `notify()` был бы недоступен из фоновых задач и cron.
- **Резолверы не попадают в схему:** core-схема собирается с `include: [CoreEngineModule]` (`graphql-config.service.ts:85`), обход идёт по импортам этого модуля (`@nestjs/graphql/dist/services/base-explorer.service.js:13-21`). `ModulesModule` в это дерево не входит, поэтому `smbNotifications` и любые будущие Query/Mutation модулей в `/graphql` отсутствовали. Спайк A2 этого не увидел: он проверял хук, а хуки находятся через `DiscoveryService` по всему приложению.

### Дефект 2. Свои таблицы были привязаны к конвейеру обновлений Twenty

Таблица уведомлений создавалась instance-командой `@RegisteredInstanceCommand('2.45.0', …)`. Конвейер `upgrade` работает **по курсору**: стартует со следующего шага после последнего выполненного (`upgrade-sequence-runner.service.ts:249-275`), а порядок внутри версии — сначала все fast-команды, потом slow, потом workspace (`upgrade-sequence-reader.service.ts:39-60`). В проде запускается только `upgrade` (`twenty-docker/twenty/entrypoint.sh:23`).

Следствия:

- Команда форка, добавленная в версию, которую сервер уже прошёл, **не выполнится никогда**. Это наш обычный случай: между обновлениями upstream мы добавим таблицы бесед, реакций, привязок Б24 — каждая на уже работающие серверы. Признак в самом репозитории: для dev-базы пришлось писать обходной скрипт `scripts/smb-notifications-migrate.ts`.
- После merge upstream команды upstream с меткой времени меньше нашей последней встают в последовательности **раньше курсора** и молча пропускаются — расхождение схемы ядра без единой ошибки.

### Дефект 3. Нет способа включить модули в новой компании без человека

Пресеты (M-6) ставят App через HTTP `/metadata` с токеном администратора компании. При установке приложения из маркетплейса Б24 компания создаётся автоматически (ADR-008 п.2) — токена ещё нет, запускать CLI некому.

## Решение

### 1. Шов P-002 — в `CoreEngineModule`

`SmbServerModule` импортируется в `src/engine/core-modules/core-engine.module.ts` (2 строки: импорт и элемент списка). Это дерево грузят сервер, воркер и CLI, и по нему собирается схема `/graphql`. `modules.module.ts` возвращён к upstream. Число серверных швов не изменилось — один.

Правило для модулей: резолверы помечаются `@CoreResolver` (попадают в `/graphql`); `@MetadataResolver` в модулях форка не используется — схема `/metadata` собирается по другому дереву (`MetadataGraphQLApiModule`), и туда наш шов не ведёт.

### 2. Свои таблицы — схема `smb` и свой журнал миграций

- Таблицы серверных частей модулей живут в отдельной схеме Postgres **`smb`** (не `core`, не схемы компаний). Каждая таблица с данными компании имеет `workspaceId` с `REFERENCES core.workspace(id) ON DELETE CASCADE` — удаление компании чистит данные без нашего кода.
- Миграция — объект `{ name, up }` в `smb-<key>/migrations/`; модуль добавляет свой список одной строкой в `smb-database/registry.ts`.
- `SmbMigrationRunnerService` при старте каждого процесса применяет миграции, которых нет в журнале `smb._migration`. Учёт **по имени**, а не по позиции; каждая миграция — в своей транзакции; `pg_advisory_lock` защищает от одновременного старта сервера и воркера; упавшая миграция останавливает запуск процесса.
- Конвейер обновлений Twenty наши таблицы не видит и не трогает: instance-команды в модулях форка **не пишутся**. Команда на workspace (`@RegisteredWorkspaceCommand`) допустима только для разового изменения метаданных компаний и только после отдельного решения.
- Имя и тело применённой миграции не меняются. Отката (`down`) нет: исправление — следующей миграцией.
- На пустой базе (первый запуск `upgrade` до создания `core`) миграции откладываются до следующего старта.

Доступ к таблицам — как в ADR-010 п.2: один репозиторий-обёртка на модуль, `workspaceId` — обязательный первый аргумент, параметризованный SQL. Сущности в core DataSource не регистрируются (его список `entities` — глоб по `engine/`, правка ядра ради этого не нужна).

### 3. Установка модулей в компанию — штатный механизм предустановленных приложений

В базе есть готовое: `ApplicationRegistrationEntity.isPreInstalled` (`application-registration.entity.ts:137`) — приложение ставится в каждую новую компанию фоновой задачей при её создании (`workspace.service.ts:1236`, `pre-installed-apps.service.ts`), для существующих — команда `install-pre-installed-apps`.

- **Базовый набор** (структура компании, задачи, уведомления, лента, отсутствия, процессы) = регистрации с `isPreInstalled: true`. Новая компания получает их без токена и без CLI — в том числе созданная шлюзом Б24.
- **Дополнительные модули** (документооборот и будущие платные) ставит серверный сервис `SmbModuleInstallService` вызовом `ApplicationInstallService.installApplication({ appRegistrationId, workspaceId })` в процессе сервера. Его зовут: эндпоинт `provision` (ADR-008), команда `yarn smb:preset install`, позже — экран администратора.
- CLI через HTTP с токеном остаётся только как инструмент разработчика.
- Регистрации приложений создаются при деплое сервера из каталога `packages/twenty-apps/smb/` — способ (локальный каталог / tarball) выбирает спайк S1.

### 4. Доставка событий пользователю — фильтр на сервере

Канал Redis на компанию (`SMB_NOTIFICATIONS_CHANNEL:<workspaceId>`) несёт полные данные события. Подписка, которую получает браузер, обязана отбирать события **на сервере** по получателю (уведомления) или по членству в беседе (сообщения). Отдать клиенту поток всей компании и фильтровать во фронте — утечка личной переписки. Один общий сервис подписки `smb-realtime` на уведомления и беседы; транспорт (свой `@Subscription` в core-схеме или штатный event stream) выбирает спайк S9.

### 5. Граница видимости: что нельзя хранить объектом компании

Объектные права Twenty — «роль видит объект целиком». Построчные права — Enterprise, использовать нельзя. Поэтому:

| Данные | Где хранить | Почему |
|---|---|---|
| Личные и групповые сообщения, уведомления, привязки пользователей Б24 | таблицы `smb.*` + резолверы модуля | видимость — по участнику |
| Отделы, отсутствия, новости, учёт времени, шаблоны задач | объекты компании (App) | видны всей компании, это нормально |
| Задачи | стандартный объект `task` | **видны всем, у кого есть право читать задачи** |

Последняя строка — расхождение с Битрикс24, где задачу видят только участники. В первой версии это ограничение принимается и записывается в руководство; «мои задачи» — это вью, а не граница доступа. Если владельцу нужна закрытость задач — отдельное решение (свои таблицы для задач = отказ от штатной карточки и канбана), вопрос O-9.

Новость с аудиторией «отдел» — по той же причине фильтр отображения, а не защита: через API запись прочитает любой участник компании.

## Последствия

- **Плюсы:** один шов работает во всех трёх процессах; модуль получает резолверы без новых правок ядра; таблицы форка не зависят от версии upstream и переживают его обновления; новая компания получает модули без ручных шагов; данные форка лежат в одной схеме — проще бэкап и перенос компании (`smb.*` по `workspaceId`).
- **Минусы:** миграции выполняются при старте — долгую миграцию данных так делать нельзя (нужна будет отдельная команда); отката миграций нет; свои таблицы не видны в общем API, поиске и экспорте Twenty — всё это пишем сами; `CoreEngineModule` — файл с частыми правками upstream (риск конфликта выше, чем у `modules.module.ts`, но правка — отдельная строка в конце списка).

## Что проверено (2026-10-12, отчёт R07 (история git))

- Сервер и воркер после переноса шва: в журнале обоих `SmbServerModule dependencies initialized`, `/healthz` → `ok`.
- Интроспекция `/graphql`: `smbNotifications`, `smbUnreadNotificationsCount`, `smbMarkAllNotificationsAsRead` присутствуют (до переноса их не было; перенос вскрыл ошибку типа поля `readAt`, скрытую тем, что резолвер не собирался в схему).
- Миграция на живом Postgres: `smb._migration` содержит `notifications/0001-create-notification-table`; тест каскада при удалении компании проходит.
- Юнит-тесты раннера: 6/6 (порядок, учёт по имени, идемпотентность, откат и снятие блокировки, пустая база, повтор имени).

## Что нужно проверить (NOT RUN)

1. **S1 (уточнён):** создать регистрацию приложения из `packages/twenty-apps/smb/<key>` с `isPreInstalled: true`, создать новую компанию — приложение установилось само; `installApplication` из серверного сервиса для необязательного модуля.
2. **S9:** подписка с серверным фильтром по получателю — второй пользователь той же компании не получает чужое событие; работает во фрейме с сессией в памяти (ADR-008 п.4).
3. PRE-хук срабатывает в воркере: шаг workflow «обновить запись» по задаче проходит через хук модуля.
4. Первый деплой на пустую базу образом форка: после `upgrade` и старта сервера схема `smb` создана.
5. Обновление upstream (регламент `docs/arch/UPSTREAM_BASE.md`): конфликт в `core-engine.module.ts` разрешается по строке P-002.
