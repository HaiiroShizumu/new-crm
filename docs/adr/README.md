# ADR — Architecture Decision Records

Архитектурные решения форка Twenty. Источник фактов — [`docs/arch/00-baseline-analysis.md`](../arch/00-baseline-analysis.md) и точечные исследования кода (ссылки `path:line` внутри ADR).

**Формат каждого ADR:** Контекст → Варианты (2–3) → Критерии → Решение (рекомендация) → Последствия → Что нужно проверить прототипом.

**Статусы:** `Предложено` → `Утверждено` / `Отменено`. Все решения сейчас в статусе **«Предложено» — окончательное утверждение за владельцем.** Утверждение фиксируется правкой строки в таблице ниже тем же коммитом, что и смена статуса в самом ADR.

## Что ADR-008…011 меняют в ранних решениях (2026-10-12)

- **ADR-002:** хранение сообщений как объектов workspace с объектными правами отменяется — для личных чатов это утечка; мост Mattermost снимается. Действует ADR-010.
- **ADR-003:** «человеческий шаг» определён как задача с формой результата; пробуждение — из серверного модуля, вариант с logic function не нужен. Действует ADR-011 п.4.
- **ADR-004:** `validationRule` остаётся для правил уровня объекта; обязательность «у каждой задачи свои поля» — PRE-хук. Действует ADR-011 п.3.
- **ADR-006:** вопрос №9 (лимит 5 workspace) снимается топологией ADR-008 — константа не правится.
- **ADR-007:** серверное размещение — рекомендация M2; число швов фиксируется таблицей ADR-009 п.4.
- **Вопросы владельцу №3 и №4** (Mattermost) ниже — закрыты ADR-010.

## Замечание о ревизиях

Аудит baseline описан по upstream `0cd095bfe8` (sdk/v2.45.0-302), а **база форка — тег `twenty/v2.45.6`** ([`docs/arch/UPSTREAM_BASE.md`](../arch/UPSTREAM_BASE.md)). Расхождения уже зафиксированы: в базе форка нет `WAIT_FOR_EVENT`/`workflow-wait`/`submitFormStep` (механика FORM-паузы — через `pendingEvent` + `answerToolCall`), см. контекст ADR-003; пересчёт `@license Enterprise` — 475 файлов против 482 в baseline §6 (см. ADR-006). Ответ на вопрос №10 ниже определяет, по какой ревизии верифицировать факты в дальнейшем.

## Вопросы владельцу (закрытые, с вариантами ответа)

1. **Живой прототип Hello module (ADR-001): запускать до утверждения?**
   (а) да, `twenty app apply` на dev-стеке; (б) нет, аналитического расчёта достаточно; (в) запустить после поднятия стека, до утверждения ADR-002.
   *Рекомендация: (в).*

2. **Основной механизм модулей (ADR-001):**
   (а) только Twenty Apps; (б) только `smb-*` + швы; (в) гибрид — Apps по умолчанию, швы по PATCHES.md.
   *Рекомендация: (в).*

3. **Mattermost (ADR-002): какой путь?**
   (а) сразу отдельный сервис; (б) фаза 1 нативно, мост — опцией позже; (в) только нативно, мост не рассматривать.
   *Рекомендация: (б).*

4. **Бюджет на Enterprise-лицензию Mattermost (если вариант 3а/3б с мостом):**
   (а) да, рассматриваем; (б) нет, только Team (без SSO) или свои клиенты; (в) вопрос снимается — мост не нужен.
   *Рекомендация: (б).*

5. **Базовая архитектура процессов (ADR-003):**
   (а) A — шаг-задание внутри workflow; (б) B — своя модель процессов; (в) C — workflow как исполнитель + слой задач.
   *Рекомендация: (в), с эволюцией в (а) при потребности в approval.*

6. **Точка проверки `requirementRules` на сервере (ADR-004):**
   (а) существующий `validationRule` в репозитории; (б) PRE-hook до транзакции; (в) обе с разделением по сценариям.
   *Рекомендация: (а), PRE-hook — только для отдельных случаев.*

7. **Список из 5 разрешённых швов визуального слоя (ADR-005) утвердить?**
   (а) утвердить как есть; (б) убрать `Logo.tsx` — логин через logo workspace; (в) иной состав (указать).
   *Рекомендация: (б) — четыре шва с churn ≤ 10, лого — через workspace-настройки.*

8. **Источник дистрибуции пресетов (ADR-006):**
   (а) свой tarball-реестр (`APP_REGISTRY_URL`); (б) приватный npm; (в) публичный npm-marketplace Twenty.
   *Рекомендация: (а).*

9. **Лимиты без Enterprise-ключа (ADR-006; верификация на `twenty/v2.45.6`):** на базе оба лимита — **на инстанс**, не на workspace: `MAX_WORKSPACES_WITHOUT_ENTERPRISE_KEY=5` (`workspaceRepository.count()` в `sign-in-up.service.ts`, константа без `@license Enterprise`); `MAX_SEATS_WITHOUT_ENTERPRISE_KEY=25` (`COUNT(DISTINCT userId)` по инстансу, константа **с** `@license Enterprise`, гейтит custom AI providers). Что делаем?
   (а) шов в `sign-in-up.service.ts` (поднять/снять лимит workspace на инстанс); (б) свой механизм Organization/Enterprise-ключа (лимиты остаются, ключ наш); (в) оставить лимиты как есть; (г) заменить оба лимита своим AGPL-гейтом в `packages/smb-*` (не трогать Enterprise-файл seats).
   *Рекомендация: (б) для workspace-лимита + (г) если нужны свои seat-пороги без Enterprise-файла.*

10. **По какой ревизии верифицировать факты в ADR?**
    (а) база форка `twenty/v2.45.6` (текущая); (б) upstream `main`; (в) база форка + перепроверка при каждом merge (по UPSTREAM_BASE).
    *Рекомендация: (в).*
