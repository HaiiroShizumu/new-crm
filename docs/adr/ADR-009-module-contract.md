## Контекст

ADR-001 выбрал «гибрид: Apps + швы», но не сказал, **из чего состоит модуль и куда класть каждую часть**. Без этого каждый новый модуль (структура компании, лента, отсутствия, документооборот) снова решает одно и то же, и швы расползаются — так устроен старый билд: условия `isMessengerEnabled && …` в общих файлах навигации и роутинга, Nest-модули в `engine/core-modules/`.

Что уже известно:

- Twenty Apps доставляют данными: объекты, поля, вью, страницы, пункты меню, роли, workflows, logic functions, переводы (`manifestType.ts:36-60`). Жизненный цикл install / upgrade / uninstall на компанию — штатный.
- Apps **не дают**: серверных CRUD-хуков, своих резолверов и REST-контроллеров, своих таблиц вне метаданных; фронт App работает в изоляции (Web Worker + Remote DOM) — WebRTC, запись с микрофона, тяжёлые редакторы там не живут.
- Фронт форка уже размещается каталогами `packages/twenty-front/src/modules/smb-*` (M2), швы P-003 и P-013.
- Для сервера выбор M1/M2 открыт. Причина, по которой фронт ушёл в M2, действует и на сервере: серверный код модуля импортирует внутренности `twenty-server` (`src/engine/...`), а `twenty-server` должен импортировать модуль — у отдельного пакета получается цикл.
- Два источника «включён ли модуль» (флаг и установленный App) расходятся при первой же ошибке установки.

## Решение (рекомендация)

### 1. Модуль = до трёх частей с одним ключом

```
smb-<key>
├── app/      packages/twenty-apps/smb/<key>/            данные: объекты, поля, вью, роли, workflows,
│                                                        пункты меню, переводы, logic functions
├── server/   packages/twenty-server/src/modules/smb-<key>/   (нужна не всем)
│             Nest-модуль: CRUD-хуки, резолверы, REST, свои таблицы, фоновые задачи
└── front/    packages/twenty-front/src/modules/smb-<key>/    (нужна не всем)
              страницы, виджеты карточки, embed-поверхность
```

Правило выбора части — сверху вниз, первая подошедшая:

| Нужно | Куда |
|---|---|
| Сущность, поле, вью, роль, пункт меню, шаблон процесса | `app/` |
| Реакция на событие без отказа пользователю (уведомить, создать запись) | `app/` — logic function |
| Отказ в сохранении, проверка до записи, свой резолвер или REST, таблица не для общего API | `server/` |
| Экран, которому мало стандартной таблицы / канбана / карточки | `front/` |

Простой модуль (график отсутствий, структура компании без схемы) — только `app/` и, возможно, одна страница во `front/`. Тяжёлый (мессенджер, документооборот) — все три.

### 2. Манифест модуля

Один файл на модуль, общий тип в `twenty-shared` нашего каталога не нужен — тип живёт в `packages/twenty-front/src/modules/smb-modules/` и зеркально в серверной части:

```ts
export const SMB_ABSENCES_MODULE = {
  key: 'absences',
  applicationUniversalIdentifier: '…uuid…', // App из части app/
  dependsOn: ['org-structure'],
  routes: [{ path: 'absences', loader: () => import('@/smb-absences/pages/AbsencesPage') }],
  navigation: [{ labelKey: 'absences.title', icon: 'IconCalendarOff', to: 'absences', group: 'company' }],
  recordTabs: [],          // вкладки в карточках чужих объектов
  embed: null,             // { path: 'embed/absences' } если модуль виден во фрейме Б24
} as const satisfies SmbModuleManifest;
```

### 3. Включён ли модуль — один источник

**Модуль включён в компании тогда и только тогда, когда его App установлен** (строка `core.application`). Отдельных feature-флагов на модуль нет. Модуль без части `app/` недопустим: даже чисто интерфейсный модуль имеет пустой App — как выключатель и носитель ролей.

- Фронт: один запрос списка установленных приложений → реестр отдаёт только маршруты, пункты меню и вкладки включённых модулей. **Реализация (M-3):** маршруты всех модулей регистрируются всегда, а страницу перекрывает `SmbModuleRouteGate` — Apollo-провайдер живёт *внутри* дерева маршрутов (`WorkspaceAppProviders`), поэтому состав установленных App при сборке роутера вычислить нельзя; пересборка роутера на каждую установку App перезапускала бы воркспейс-часть целиком.
- Сервер: guard `@RequireSmbModule('<key>')` на резолверах и контроллерах модуля проверяет то же по кэшу.
- Пресет (ADR-006a) = список ключей модулей; установка пресета = установка их App в порядке `dependsOn`.
- Выключение модуля не удаляет данные молча: uninstall App каскадно удаляет его объекты, поэтому команда `smb:module disable` по умолчанию только снимает доступ (роль), а удаление данных — отдельный явный шаг с подтверждением.

### 4. Швы ядра — фиксированное число, не растёт с модулями

| ID | Файл | Что | Состояние |
|---|---|---|---|
| P-002 | `packages/twenty-server/src/modules/modules.module.ts` | импорт `SmbServerModule`, который собирает `server/` всех модулей | **реализован 2026-10-12** (место подтверждено прогоном S-A2; сам корень лежит в `modules/smb-server.module.ts`) |
| P-003, P-013 | `index.tsx`, `SharedAppProviders.tsx` | скин | реализованы |
| P-014 | `createWorkspaceRouteObjects.tsx` (churn 7 за 6 мес.) | 3 строки: импорт, комментарий и spread маршрутов из реестра модулей | реализовано (M-3) |
| P-015 (резерв) | точка сборки оболочки (layout) | одна строка: наша оболочка вместо штатной | новый, см. п.5 |

Новый модуль **не добавляет швов**: он регистрируется в двух наших файлах — `smb-modules/registry.ts` (фронт) и `smb-server.module.ts` (сервер). Если модулю нужен новый шов — это отдельный ADR, а не правка «по месту».

Серверное размещение: рекомендация — M2 (`packages/twenty-server/src/modules/smb-*`), по той же причине цикла, что и на фронте. Это расширение паттерна OURS в гейте → отдельный коммит, ревью владельца, bats-кейсы (правило форка). **Выполнено 2026-10-12** (TODO M-1, кейсы M1-1…M1-5, `docs/reports/R06.md` §1); замер M1/M2 из A2 п.2.1 остаётся открытым.

### 5. Интерфейс: оболочка наша, движки записей — штатные

Требование «интерфейс новый, старого Twenty не будет» выполняется на уровне, который видит пользователь, без переписывания всего фронта:

- **Наше целиком:** оболочка (боковая панель, верхняя панель, главная, переключение разделов), страницы модулей, скин и токены. Источник — `new-crm-master` (`smb-skin`, форковая navigation, `ui-preferences`), перенос по методике R04.
- **Штатное под нашим скином:** таблица записей, канбан, карточка записи, фильтры, редактор workflow, настройки модели данных. Это десятки тысяч строк самого изменчивого кода upstream; переписать их — значит навсегда отказаться от обновлений фронта.

Это решение совместимо и с «путём A» (живые обновления), и с «путём B» (заморозка базы): швов мало в обоих случаях. Если владелец хочет заменить и движки записей — это отдельное решение с оценкой, и оно фактически означает путь B для фронта.

### 6. Сторонние и клиентские модули

Клиент или партнёр пишет модуль **только как App** (часть `app/`), без доступа к репозиторию: `twenty app init/apply`. Части `server/` и `front/` — только у модулей, которые собираем мы.

## Последствия

- **Плюсы:** у каждого вида работы одно место; модуль добавляется без новых патчей ядра; включение проверяется одинаково на фронте и сервере; простые модули остаются простыми.
- **Минусы:** код модулей первого класса входит в общий бандл и образ — «выключен» значит «недоступен», а не «отсутствует»; три части надо версионировать согласованно (версия App должна соответствовать коду в образе — проверка при старте); зависимость от механизма Apps, самой изменчивой зоны upstream.
- **Процессно:** генератор `yarn smb:module new <key>` создаёт три каталога, манифест и строки в двух реестрах — чтобы «добавить модуль» было одной командой и одним шаблоном.
