## Контекст

ADR-002 решал только «обсуждение в карточке записи». Требование шире: личные и групповые чаты, голосовые сообщения, аудио- и видеозвонки, чат задачи, комментарии ленты новостей. В старом билде мессенджер — фасад над Mattermost (`new-crm-master/.../core-modules/mattermost/`, 48 файлов фронта `modules/messenger`).

### Оценка Mattermost под это требование

| Требование | Mattermost (бесплатная Team Edition) |
|---|---|
| Групповые звонки | нет: «для групповых звонков нужен Enterprise, Professional или Cloud»; бесплатно — только 1:1 |
| Видео | экспериментально, только в личных звонках, выключено по умолчанию, в мобильном приложении нет |
| Голосовые сообщения | в документации звонков и сообщений не упоминаются |
| Пользователи | по сообщениям сообщества, в v11 предел Team Edition снижен до 250 на инстанс (первоисточник не проверен) — ровно наши 5 × 50 |
| Компании на одном сервере | нужно отображение «компания → team», своя модель прав, второй каталог пользователей и его синхронизация |
| Чат задачи и ленты | канал на каждую задачу — провижининг и права, не совпадающие с правами записи |
| Эксплуатация | +2 контейнера и отдельная БД на каждый сервер |

Источник по звонкам: https://docs.mattermost.com/end-user-guide/collaborate/make-calls.html (прочитано 2026-10-12).

**Вывод: Mattermost не подходит.** Он закрывает текстовый чат, который и так проще всего, и не закрывает то, ради чего его рассматривали (групповые звонки, видео, голосовые), при этом приносит вторую систему пользователей и прав.

### Альтернативы

| Вариант | Голосовые | Звонки | Почему нет / да |
|---|---|---|---|
| Matrix (Synapse + Element Call) | да | да, через LiveKit | всё есть, но это отдельная федеративная платформа: свой каталог пользователей, комнаты вместо наших бесед, тяжёлый сервер, AGPL; интеграция дороже своего чата |
| Rocket.Chat | — | через Jitsi / BigBlueButton | бесплатный Starter — до 50 пользователей, Community — до 100 одновременных и «не для продакшена» по словам вендора |
| Zulip | нет | нет своих (ссылка на Jitsi) | не закрывает требование |
| **Свой чат + LiveKit** | да (файл-вложение) | да, аудио, видео, экран, группы | рекомендация |

LiveKit — SFU с открытым кодом (Apache 2.0), ставится одним контейнером со встроенным TURN; у Matrix/Element Call звонки построены на нём же.

## Решение (рекомендация)

### 1. Одна модель бесед на всё

Модуль `smb-conversations` (части `server/` и `front/` по ADR-009):

- `conversation` — `kind: DIRECT | GROUP | RECORD | FEED_POST`; для `RECORD` и `FEED_POST` — ссылка на объект и запись.
- `conversationMember` — участник, роль, `lastReadSeq`, `isMuted`.
- `message` — `seq` (монотонный в беседе), автор, `kind: TEXT | VOICE | FILE | SYSTEM | CALL`, текст, вложения, ответ на сообщение, правка, мягкое удаление; реакции.

Личный чат, групповой чат, чат задачи и комментарии к новости — одна и та же беседа с разным `kind`. Один компонент ленты сообщений на фронте, один механизм непрочитанного и уведомлений.

### 2. Исправление ADR-002: сообщения — не объекты метаданных

ADR-002 предлагал хранить треды и сообщения как объекты workspace с объектными правами роли. Для личных чатов это **утечка**: объектное право «читать `message`» даёт через общий GraphQL и REST доступ ко **всем** сообщениям компании, включая чужую личную переписку. Построчных прав без Enterprise нет, и использовать их запрещено.

Поэтому:

- таблицы бесед — **свои таблицы серверной части модуля** (TypeORM-сущности в нашем каталоге, колонка `workspaceId`, миграции instance-командами), в общий API записей не попадают;
- доступ — **только через резолверы модуля**, каждый запрос проходит одну функцию проверки:
  - `DIRECT`, `GROUP` — пользователь есть в `conversationMember`;
  - `RECORD` — у роли есть право чтения объекта записи и запись существует (проверка штатным сервисом прав, не своей копией);
  - `FEED_POST` — пользователь входит в аудиторию новости;
- фильтр по `workspaceId` ставится в одном репозитории-обёртке, прямой доступ к сущностям из резолверов запрещён (правило линтера + тест «запрос из компании A не видит беседу компании B»).

Цена: поиск по сообщениям, экспорт и удаление вместе с компанией строим сами (каскад по `workspaceId` при удалении workspace — обязательный тест).

### 3. API — сохранить фасад старого билда

Старый фронт мессенджера ходит в шесть операций: `messengerConversations`, `messengerMessages`, `sendMessengerMessage`, `markMessengerConversationAsRead`, `sendMessengerTyping`, подписка `onMessengerEvent`. Новый сервер реализует **тот же контракт** на своих таблицах, поэтому 48 файлов фронта переносятся с заменой только источника данных. Контракт расширяется: создание беседы, участники, реакции, правка и удаление, вложения, звонки.

Доставка в реальном времени — существующая связка Redis pub/sub + подписки (SSE), новых сервисов нет.

### 4. Голосовые сообщения

Запись в браузере (`MediaRecorder`, Opus) → загрузка в штатное файловое хранилище → сообщение `kind: VOICE` с длительностью и огибающей громкости для отрисовки. Проверить Safari (контейнер mp4/aac вместо webm) — при расхождении перекодирование на сервере не делаем, отдаём оба формата как есть и проигрываем нативно.

### 5. Звонки — LiveKit на каждом инстансе

- Один контейнер LiveKit на сервер, комнаты `ws_<workspaceId>_<conversationId>` — компании изолированы именем комнаты и токеном.
- Токен комнаты выдаёт **наш сервер** после той же проверки доступа к беседе (п.2); срок жизни — минуты; права публикации из роли участника.
- Вызов и «звонит…» — событие в нашем канале подписок; звонок оставляет в беседе сообщение `kind: CALL` (кто, когда, длительность, пропущен).
- Звонок возможен в беседе любого вида, включая чат задачи.
- Сеть: 443/tcp (сигнализация через Caddy), 7881/tcp, 7882/udp, при необходимости 3478/udp (TURN). Это **новые открытые порты** на сервере — учесть в `docs/ops/deploy.md` и firewall.
- Запись звонков — вне первой версии.

### 6. Уведомления — общий платформенный модуль

Модуля уведомлений в Twenty нет, а он нужен всем: задачи, чаты, лента, процессы, отсутствия. Модуль `smb-notifications`:

- таблица `notification(recipient, kind, sourceModule, payload, readAt)` — своя, как беседы;
- любой модуль отправляет через один серверный сервис `notify(recipient, kind, payload)`; дедупликация по ключу события;
- каналы: колокольчик и счётчик в оболочке (подписка), email-сводка с задержкой для непрочитанного; push в браузере — позже;
- настройки пользователя «что и куда присылать» — один экран.

Делается **раньше** задач 2.0 и мессенджера: они оба от него зависят.

## Последствия

- **Плюсы:** одна модель и один UI на четыре требования; права беседы совпадают с правами записи по построению; никакого второго каталога пользователей; изоляция компаний — наш `workspaceId`; фронт старого мессенджера переиспользуется.
- **Минусы:** чат, непрочитанное, поиск, уведомления — наш код и наша поддержка; LiveKit — новый сервис и открытые UDP-порты, нагрузка на CPU и канал растёт с числом участников видео; мобильных приложений нет (только адаптивный веб); свои таблицы мимо метаданных — значит свои миграции и свой экспорт.
- **Процессно:** код `core-modules/mattermost` старого билда не переносится; из него берётся только контракт GraphQL и DTO.

## Что нужно проверить (NOT RUN)

1. **S2 (переформулирован):** лента на 10 000 сообщений, кириллица с IME, упоминания, подписка — в нашем модуле фронта (не в Remote DOM: App-виджет для чата больше не рассматривается).
2. Тест изоляции: компания A / компания B; участник беседы / не участник; роль без права чтения `task` не читает чат задачи — через GraphQL и через подписку.
3. LiveKit на одном сервере рядом с Twenty: память и CPU при 3 одновременных звонках по 6 участников с видео; работа из сети с закрытым UDP (TCP 7881 / TURN).
4. Голосовое: запись и воспроизведение Chrome ↔ Safari ↔ Firefox.
5. Каскадное удаление данных бесед и уведомлений при удалении workspace.
6. Подписки (SSE) во фрейме Б24 с сессией в памяти (ADR-008 п.4).

## Поправка 2026-10-13: что реализовано и чем отличается (отчёт R11)

Реализованы п.1–3 в части личных и групповых бесед. Отличия от текста выше:

- **п.3, контракт фасада.** Имена шести операций сохранены (`messengerConversations`,
  `messengerMessages`, `sendMessengerMessage`, `markMessengerConversationAsRead`, `sendMessengerTyping`,
  `onMessengerEvent`), но аргумент — `conversationId`, а не `colleagueWorkspaceMemberId`: старый
  контракт знал только личные диалоги. Фронт написан заново, старый фронт с этим API не заработает.
- **п.1, имена таблиц.** `smb.conversation`, `smb.conversationMember`, `smb.conversationMessage`
  (camelCase, как `smb.notification`), а не `conversation_member` и `message`.
- **п.1, `isMuted`.** Вместо флага хранится `mutedUntil` (момент, до которого беседа заглушена):
  «заглушить на час» и «навсегда» выражаются одним полем.
- **Модуль платформенный.** У `smb-conversations` нет App-выключателя, как и у `smb-notifications`:
  мессенджер есть в каждой компании. В манифесте фронта это `isPlatform: true`.
- **Поток событий.** Один поток на человека, сервер публикует событие в Redis-топик каждого
  участника (`SMB_CONVERSATION:<workspaceId>:<workspaceMemberId>`); это закрывает требование ADR-013 п.4
  «событие получает только адресат» без фильтра на стороне подписки.
- **Имперсонация.** Сеансы имперсонации к операциям бесед не допускаются.
- **Идемпотентность.** Клиент присылает `clientMessageId`; повтор отправки возвращает уже
  сохранённое сообщение. Номер `seq` и вставка — один SQL-оператор.

Не реализовано: `RECORD` и `FEED_POST`, реакции, вложения, ответы, голосовые (п.4), звонки (п.5),
уведомления об упоминаниях (п.6), поиск. Проверки №1–5 из раздела выше остаются NOT RUN.
