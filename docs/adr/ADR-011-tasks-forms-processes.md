# ADR-011: Задания с формой результата и процессы с ручным запуском

**Статус:** Утверждено владельцем 2026-10-12 (TODO O-1)
**Дата:** 2026-10-12
**Основание:** вход владельца 2026-10-12 (процессы запускаются вручную с параметрами — «заявление на отпуск: даты, причина»; задачи с обязательными полями, разными у каждой задачи; учёт времени); [ADR-003](ADR-003-business-processes.md), [ADR-004](ADR-004-required-fields-rules.md)
**Связанные:** [ADR-009](ADR-009-module-contract.md), [ADR-010](ADR-010-communications.md)
**Уточняет:** ADR-003 (чем именно является «человеческий шаг») и ADR-004 (его правила — про объект целиком, а не про отдельную задачу)

---

## Контекст

Два требования выглядят разными, но это одна вещь — **форма, которую заполняет человек**:

1. Процесс запускается вручную, и запускающий вводит параметры (даты отпуска, причина).
2. Исполнителю приходит задача, которую нельзя закрыть, пока не заполнены обязательные поля; у разных задач поля разные.

Факты на базе (прочитано, не запускалось):

- Ручной триггер умеет запускаться без записи: `availability.type: 'GLOBAL'` (`manual-trigger-schema.ts:16-33`).
- Шаг `FORM` есть (`WorkflowActionType.ts:14`, `form-action-schema.ts`): пауза до ответа человека, значения полей доступны следующим шагам.
- ADR-004 опирается на `validationRule` — правило на **объект** («у всех задач в статусе X обязательно поле Y»). Требование «у каждой задачи свой набор полей» им не выражается: набор полей — данные конкретной задачи, а не схема объекта.
- ADR-003 выбрал «человеческий шаг = запись `task`», но не определил, что исполнитель в ней заполняет и как это возвращается в процесс.

## Решение (рекомендация)

### 1. Ручной запуск с параметрами — штатно, без кода ядра

Шаблон процесса = workflow с триггером `MANUAL` + `availability: GLOBAL`, **первый шаг — `FORM`** с параметрами запуска. «Заявление на отпуск»: форма (с, по, причина) → задание руководителю (п.2) → ветка согласовано / отклонено → запись в графике отсутствий → уведомление.

Наша работа — только подача:

- раздел оболочки «Процессы → Запустить» со списком опубликованных процессов, доступных роли пользователя;
- «Мои запуски» с состоянием и текущим шагом;
- шаблоны процессов поставляются в `app/` модулей (`workflows[]` манифеста).

Если шаг `FORM` первым шагом при глобальном запуске поведёт себя не так, как нужно (спайк S4a) — запасной вариант: параметры собирает наша форма запуска и передаёт их в payload ручного триггера. Движок workflow в обоих случаях не правится.

### 2. Задание с формой результата

К стандартному объекту `task` модуль `smb-tasks` добавляет поля (через `app/`):

| Поле | Тип | Смысл |
|---|---|---|
| `resultForm` | RAW_JSON | описание полей результата: `[{ key, label, type, isRequired, options? }]` |
| `resultValues` | RAW_JSON | заполненные значения |
| `taskTemplate` | связь | шаблон задачи, из которого взята форма (необязательно) |
| `workflowRunId`, `workflowStepId` | текст | задание выдано шагом процесса |
| `outcome` | SELECT | `APPROVED / REJECTED / DONE` — для согласований |

Формат описания полей — **тот же, что у шага `FORM`** (`form-action-settings-schema.ts`): один редактор формы и один компонент отрисовки на запуск процесса, шаг процесса и результат задачи.

Откуда берётся форма у задачи:

- постановщик добавляет поля при создании («приложите номер договора»);
- задача создана из шаблона `taskTemplate` — форма копируется (копия, а не ссылка: правка шаблона не меняет выданные задачи);
- задачу создал шаг процесса — форма задана в шаге.

### 3. Где проверяется обязательность

**На сервере, PRE-хуком `task.updateOne` / `updateMany`** в серверной части модуля: переход в завершающий статус отклоняется, если в `resultValues` нет значения для поля с `isRequired`. Ошибка — с ключом поля, чтобы фронт подсветил его.

Почему хук, а не `validationRule`: правило зависит от данных самой записи (`resultForm`), язык выражений `validationRule` для этого не изучен и находится за флагом; хук срабатывает одинаково для карточки, канбана, inline-правки, API и импорта. `validationRule` из ADR-004 остаётся для правил уровня объекта («в работе — обязателен исполнитель»).

Фронт: в карточке задачи блок «Результат» с формой; кнопка «Завершить» открывает форму, если она не заполнена; перетаскивание на канбане в завершающую колонку при пустых обязательных полях открывает ту же форму, а не показывает сырую ошибку сервера.

### 4. Задание как шаг процесса

Шаг процесса «Задание» = создать `task` с `resultForm`, `workflowRunId`, `workflowStepId` и исполнителем → процесс ждёт. Когда задача завершена (хук из п.3 уже пропустил её), процесс продолжается с `resultValues` и `outcome` как выходом шага.

Пробуждение — тот же серверный модуль после COMMIT вызывает штатное `resumeAnsweredStep` (`workflow-runner.workspace-service.ts:109`). Раз серверная часть у модуля всё равно есть (п.3), вариант «logic function + публичная мутация» из поправок ADR-003 не нужен: одна точка, одна транзакционная граница. Обязательные свойства: идемпотентность (повторное завершение не будит процесс дважды), удаление задачи останавливает ожидание с понятным состоянием запуска.

Исполнитель шага задаётся одним из способов: конкретный участник, «руководитель запустившего» (из структуры компании), «руководитель отдела X», роль. Разрешение «кто это» — сервис модуля структуры компании.

### 5. Учёт времени

Объект `timeEntry` в `app/` модуля задач: задача, участник, начало, конец, минуты, комментарий. Таймер «старт / стоп» в карточке и ручной ввод. Серверное правило (тот же модуль): у участника не больше одного незавершённого таймера. Сумма по задаче — вычисляемое отображение, не хранимое поле. Плановая оценка — поле `estimateMinutes` у задачи.

### 6. Чат задачи

Беседа `kind: RECORD` из ADR-010, вкладка в карточке. Отдельной модели нет.

### Чего в этой версии нет (записать в руководство, не обещать клиентам)

Отката процесса на шаг назад, делегирования задания с сохранением истории, подзадач, эскалации по SLA сверх уведомления о просрочке. Каждое — отдельное решение после первой версии.

## Последствия

- **Плюсы:** один формат и один компонент формы на три места; движок workflow не правится; обязательность нельзя обойти ни через какой интерфейс; «Мои задания» — готовая вью задач.
- **Минусы:** значения результата лежат в JSON — по ним нет фильтров и колонок в таблице задач (для отчётов по конкретному полю его надо заводить настоящим полем); связь «задача ↔ шаг запуска» — наша дисциплина согласованности при долгих процессах; модуль зависит от формата настроек шага `FORM`, который upstream может менять.
- **Процессно:** серверный PRE-хук задач — первый реальный потребитель шва P-002; прототип Discovery из ADR-007 делается на нём.

## Что нужно проверить (NOT RUN)

1. **S4a:** глобальный ручной запуск с первым шагом `FORM` — где пользователь видит форму, что происходит при закрытии без ответа.
2. **S4 (из плана):** `resumeAnsweredStep` из серверного модуля после COMMIT будит запуск; повторный вызов безопасен.
3. **S3 (переформулирован):** PRE-хук отклоняет завершение; что показывает канбан и inline-правка, откатывается ли оптимистичное обновление.
4. App добавляет поля на стандартный `task` (общий пункт с ADR-009 №2).
5. Контрактный тест на формат настроек шага `FORM` — падает при изменении upstream.
6. Публикация новой версии процесса при ждущем задании не рвёт связь.
