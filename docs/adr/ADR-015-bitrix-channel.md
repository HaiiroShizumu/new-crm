# ADR-015: Канал Битрикс24 (одна ссылка приложения, вход без пароля, авторегистрация)

## Контекст

Приложение в маркетплейсе Б24 имеет один адрес обработчика на все порталы. У нас при этом у каждой
компании свой workspace на своём сабдомене. Сотрудник портала должен сразу попасть в свой аккаунт
без пароля, а все сотрудники должны получить аккаунты при установке.

Старый билд (`company-tunnel`, v2.42.6) решал это проверкой `application_token` и REST-вызовами на
домен из тела запроса. Его слабые места разобраны в S6: нет белого списка доменов, первый install
идёт без эталона токена, привязка по email.

## Решения

1. **Модуль `modules/smb-bitrix`, подключён в `SmbServerModule`.** Три адреса под
   существующим префиксом `webhooks/`: `POST /webhooks/smb-bitrix/install`, `/app`, `/event`.
   Префикс существующий, потому что любой другой GET с `Accept: text/html` сервер отдаёт как
   документ фронта, а новое значение `ApiPath` было бы ещё одной правкой ядра.

2. **Единственное доказательство запроса это обмен `REFRESH_ID` на oauth.bitrix.info с нашим
   `client_secret`.** Из тела запроса берётся только refresh-токен. Идентификатор портала
   (`member_id`), адрес его REST и токены берутся из ответа сервера авторизации Б24. Отсюда:
   - поддельный `member_id` или `DOMAIN` в теле ни на что не влияют;
   - токен, выданный чужому приложению, обмен не пройдёт;
   - белый список доменов не нужен, коробочные порталы на своих доменах работают так же;
   - первый install не отличается от остальных, проблемы «нет эталона» нет.
   Адрес REST всё равно сужается до `https://<host>/rest/` и проверяется на внутренние IP перед
   каждым вызовом.

3. **Две таблицы в схеме `core`:** `smbBitrixPortal` (портал → workspace, зашифрованные токены,
   статус `PENDING | ACTIVE | UNINSTALLED`) и `smbBitrixUser` (портал, id пользователя Б24 → `user`).
   Таблицы уровня инстанса: по строке портала и выясняется, чей это workspace.

4. **Личность сотрудника это пара (портал, id в Б24), а не email.** Email используется один раз,
   чтобы создать или найти аккаунт. Существующий аккаунт привязывается по email, только если он не
   состоит ни в каком другом workspace и не является администратором сервера. Причина: email
   сотрудников задаёт администратор портала, а сессия в одном workspace умеет переходить в другие
   workspace того же пользователя (`setLoginTokenToAvailableWorkspacesWhenAuthProviderMatch`). Без
   этого правила портал мог бы войти в чужую компанию, вписав чужой email. В остальных случаях
   сотрудник видит сообщение «обратитесь к администратору», привязка делается вручную (TODO D5).

5. **Вход без пароля.** `/app` выдаёт штатный login-token и отвечает `303` на
   `<сабдомен>/verify?loginToken=…&returnToPath=/docflow`. Дальше работает штатная страница
   `/verify`. Аккаунты создаются с `isEmailVerified = true` и без пароля: за сотрудника ручается
   портал, а без этого флага сервер с обязательным подтверждением почты не пустил бы никого.
   Экран «создайте профиль» для них отключается, имя уже пришло из портала.

6. **Cookie в iframe (P-032).** Токены сессии фронт хранит в cookie с `SameSite=Lax`. Внутри
   фрейма чужого сайта такие cookie браузер не сохраняет. Во встроенном режиме ставится
   `SameSite=None; Secure; Partitioned`. Это главный риск всего канала, и он проверяется только на
   живом портале в Chrome, Safari и Firefox (эксперимент E1 из S6).

7. **Встроенный режим определяется фактом фрейма** (`window.self !== window.top`), без параметра в
   адресе. В нём скрыта боковая навигация (P-033), в шапке документооборота появляются кнопки «На
   весь экран» и «Открыть CRM».

8. **«На весь экран»** это штатный слайдер портала: `BX24.openApplication` открывает приложение
   второй раз поверх страницы, развёрнутая копия закрывается через `BX24.closeApplication`. Флаг
   развёрнутости едет через `PLACEMENT_OPTIONS` и `returnToPath`.

9. **«Открыть CRM»** открывает сабдомен в новой вкладке. Мутация `createSmbBitrixCrmLink`
   возвращает ссылку: если пароля ещё нет, это штатная `/reset-password/<токен>` (email там уже
   подставлен, человек придумывает пароль), иначе `/verify?loginToken=…`. Вкладка нужна, потому что
   сессия фрейма лежит в partitioned-хранилище и верхнему окну не видна. Имперсонированным сессиям
   ссылка не выдаётся.

10. **Авторегистрация при установке.** `/install` требует администратора портала (`user.admin`),
    разрешает домену портала встраивать workspace (`allowedIframeOrigins`), затем в фоне читает
    `user.get` (активные сотрудники, до 2000) и создаёт аккаунты по одному. Кого синхронизация не
    успела создать, тот создаётся при первом открытии приложения.

11. **Создание workspace при установке выключено по умолчанию**
    (`SMB_BITRIX_AUTO_PROVISION_WORKSPACE=true` включает). Причины: лимит 5 workspace на инстанс
    до ответа юриста и нерешённый wildcard-сертификат. Без флага портал остаётся `PENDING`, и
    оператор привязывает его к workspace вручную (TODO D4). С флагом используется штатная пара
    `signUpOnNewWorkspace` + `activateWorkspace`, все ограничения ядра действуют.

12. **Удаление.** Событие `ONAPPUNINSTALL` приходит без OAuth-токенов. Оно принимается только при
    совпадении `application_token`, сохранённого из доказанного `ONAPPINSTALL` один раз и больше не
    перезаписываемого. Портал помечается `UNINSTALLED`, токены стираются, аккаунты и привязки
    остаются, повторная установка возвращает ту же компанию.

## Правки ядра

P-031 (экспорт двух сервисов из `AuthModule`), P-032 (cookie во фрейме), P-033 (полноэкранный режим во
фрейме). Миграция — в реестре миграций форка, правкой ядра не является.

## Последствия

- Для работы нужны `SMB_BITRIX_CLIENT_ID` и `SMB_BITRIX_CLIENT_SECRET` тиражного приложения.
  Локальное приложение Б24 (без OAuth-клиента) этим каналом не обслуживается.
- Каждое открытие приложения это один запрос к oauth.bitrix.info. Обмен ротирует refresh-токен.
- В workspace должен быть включён вход по паролю: login-token выдаётся с провайдером `password`.
  Обязательная 2FA в workspace вход из Б24 остановит на шаге 2FA.
- Сотрудник без email в профиле Б24 не войдёт.

## Не проверено

- Поведение cookie во фрейме в трёх браузерах (E1).
- Не ломает ли серверный обмен refresh-токена работу `BX24` JS в том же фрейме (E3).
- Есть ли `user_id` в ответе обмена. Код не полагается на него: без него спрашивает `user.current`.
- Точный состав POST-полей при открытии приложения и в `ONAPPINSTALL`. Разбор покрыт тестами на
  обе известные формы, но сверить с живым запросом.
- Запуск сервера с модулем (DI), миграция на реальной БД.

## Поправка 2026-10-13: что изменилось при переносе в рабочее дерево (отчёт R13)

- Модуль лежит в `packages/twenty-server/src/modules/smb-bitrix` и подключён в
  `smb-server.module.ts` (шов P-002 в `core-engine.module.ts`, ADR-013 п.1).
- Таблицы — `smb.bitrixPortal` и `smb.bitrixUser`, миграция `bitrix/0001-create-portal-and-user-tables`
  в `smb-bitrix/migrations` (ADR-013 п.2). Instance-команды и TypeORM-сущностей нет, доступ — через
  `SmbBitrixRepository` на параметризованном SQL.
- `smb.bitrixPortal` — исключение из правила «`workspaceId NOT NULL`»: портал регистрируется при
  установке, до привязки к компании; при удалении компании строка остаётся отвязанной.
- Мутация `createSmbBitrixCrmLink` объявлена в схеме `/graphql` (`@CoreResolver`).
- Соотношение с ADR-008 (шлюз перед несколькими серверами): этот модуль — сторона инстанса. Адрес
  приложения в кабинете вендора Б24 при одном сервере указывает прямо на него; при нескольких —
  на шлюз, который пересылает запрос на нужный сервер. Шлюз не написан.

## Поправка 2026-10-13 (вторая): что нужно автоматическому созданию компании

Проверено чтением кода ядра (`sign-in-up.service.ts`, `assertWorkspaceCreationAllowed`), на портале не
запускалось.

- П.11 называл две причины, почему флаг выключен: лимит 5 компаний и wildcard-сертификат. Есть
  третья: `IS_WORKSPACE_CREATION_LIMITED_TO_SERVER_ADMINS` по умолчанию `true`, и тогда
  `signUpOnNewWorkspace` отказывает любому, кто не администратор сервера. Установивший приложение
  им не является. Без `false` в окружении автоматически создаётся только первая компания на пустом
  сервере. Переменная проброшена в `smb/deploy/docker-compose.yml` со значением ядра по умолчанию.
- `false` открывает создание компаний и на публичной странице регистрации. Закрыть это без правки
  ядра можно только на уровне прокси (не отдавать страницу регистрации наружу) или шлюзом из
  ADR-008. Решение по каждому серверу принимает владелец.
- Ручная привязка сделана: команда `smb:bitrix:bind-portal` (п.11). После неё аккаунты сотрудников
  создаются при первом открытии приложения, массовой синхронизации нет.

## Проект: привязка сотрудника, чей аккаунт уже существует (к п.4)

Не реализовано. Когда email сотрудника портала совпал с аккаунтом, который состоит в другой
компании или принадлежит администратору сервера, сотрудник видит «An account with your email
already exists».

Ограничение проекта: подтверждения администратора компании недостаточно. Администратор компании и
администратор портала обычно один человек, и если хватает его кнопки, правило п.4 обходится в два
клика. Согласие должен дать владелец аккаунта.

- Таблица `smb.bitrixLinkRequest` (миграция `bitrix/0002-…`): `portalId`, `bitrixUserId`,
  `workspaceId`, `email`, `fullName`, `reason` (`ACCOUNT_IN_OTHER_WORKSPACE | SERVER_ADMIN`),
  `status` (`PENDING | APPROVED | CONFIRMED | REJECTED | EXPIRED`), `tokenHash`, `tokenExpiresAt`,
  `resolvedByUserId`. Уникальность по `(portalId, bitrixUserId)`. Строка пишется там, где сейчас
  бросается отказ.
- Администратор видит список «Битрикс24: сотрудники без привязки» и получает уведомление о новой
  строке.
- Шаг 1: администратор нажимает «Запросить привязку»; на email аккаунта уходит письмо с одноразовой
  ссылкой на 24 часа, в базе хранится только хэш токена.
- Шаг 2: владелец аккаунта открывает ссылку (GET показывает страницу, POST подтверждает, чтобы
  почтовые сканеры не подтверждали за человека). Сервер добавляет пользователя в компанию и пишет
  привязку `(портал, id в Б24) → user`.
- Второй путь: «Создать отдельный аккаунт» с другим email.
- Причина `SERVER_ADMIN` не привязывается никогда.

Правок ядра не требует: отправка письма и добавление в компанию это экспортированные сервисы.
