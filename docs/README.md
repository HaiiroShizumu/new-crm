# KeySpace CRM — форк Twenty для МСБ с каналом Битрикс24

Единая точка входа в документацию форка. Очередь работ — [`../TODO.md`](../TODO.md).
Состояние на 2026-10-13.

## 1. Что это

CRM для малого и среднего бизнеса на базе Twenty (`twenty/v2.45.6`, upstream `twentyhq/twenty`).
Второй канал продаж — приложение в маркетплейсе Битрикс24: оно открывается во фрейме портала,
сотрудник входит без пароля, а полная CRM живёт на сабдомене компании.

Целевой сценарий установки из маркетплейса:

1. Администратор портала ставит приложение.
2. Сервер сам создаёт компанию: workspace на своём сабдомене и его схему в базе.
3. Сотрудники портала получают аккаунты.
4. Любой сотрудник открывает приложение в Б24 и сразу попадает в свой аккаунт.

Код этого сценария написан (раздел 4). На живом портале он не запускался ни разу: нет тиражного
приложения Б24 и сервера с доменом.

Топология: много серверов, на каждом один инстанс и до 5 компаний (лимит ядра без
Enterprise-ключа, константа не правится). Перед серверами планируется шлюз с постоянным адресом
приложения (ADR-008), он не написан; при одном сервере адрес приложения указывает прямо на него.

## 2. Правила форка

Полный текст — `../CLAUDE.md`, раздел «Форк». Коротко:

- Свой код лежит только в своих каталогах: `docs/`, `scripts/`, `smb/`,
  `packages/twenty-front/src/modules/smb-*`, `packages/twenty-server/src/modules/smb-*`,
  `packages/twenty-apps/smb/`, `.github/workflows/fork-*`.
- Любая правка файла ядра записывается строкой в [`PATCHES.md`](PATCHES.md); больше одной строки —
  ещё и ADR. Проверяет `scripts/check-core-patches.sh` (в pre-commit и в CI).
- Обновление с upstream — по [`arch/UPSTREAM_BASE.md`](arch/UPSTREAM_BASE.md), конфликты решаются
  только по реестру правок.
- «Готово» пишется с выводом запущенной команды; не запускалось — `NOT RUN` и причина.
- `locales/*.po` и `locales/generated/*` не коммитятся вне задач про переводы.

Сейчас в реестре 27 правок ядра (номера P-001…P-034, часть номеров снята или не использована). Серверный
шов один: импорт `SmbServerModule` в `core-engine.module.ts` (P-002).

## 3. Как устроен код

```
packages/twenty-server/src/modules/
  smb-server.module.ts     единственная точка подключения сервера (шов P-002)
  smb-database/            схема `smb`, свой журнал и раннер миграций
  smb-config/              настройки форка из окружения (SMB_*)
  smb-modules/             реестр модулей, guard @RequireSmbModule, GET /healthz/smb
  smb-notifications/       уведомления
  smb-conversations/       мессенджер
  smb-bitrix/              канал Битрикс24
  smb-org-structure | smb-absences | smb-feed | smb-tasks
packages/twenty-front/src/modules/
  smb-shell/ smb-skin/ smb-brand/ smb-ui-preferences/   оболочка и визуал
  smb-modules/             реестр манифестов, маршруты и пункты меню модулей
  smb-conversations/       страница /messenger
  smb-docflow/ smb-embed/  страница /docflow; работа во фрейме Б24
  smb-org-structure | smb-absences | smb-feed | smb-tasks
packages/twenty-apps/smb/  приложения модулей: объекты, поля, вью, роли
smb/deploy/                compose, Caddyfile, скрипты деплоя и бэкапа
smb/dev/                   локальное окружение, pre-commit
```

Модуль — это три каталога с одним ключом: приложение (данные), сервер, фронт. Модуль включён в
компании, когда его приложение установлено; платформенные модули (мессенджер, уведомления, пока и
документооборот) включены всегда. Как писать модуль — [`dev/module-authoring.md`](dev/module-authoring.md).

Свои таблицы живут в схеме `smb` и создаются миграциями форка, а не механизмом Twenty (ADR-013).

## 5. Установка из маркетплейса Битрикс24

Решение — [`adr/ADR-015-bitrix-channel.md`](adr/ADR-015-bitrix-channel.md), памятка оператору —
[`ops/bitrix-app.md`](ops/bitrix-app.md).

У приложения три адреса на сервере: `POST /webhooks/smb-bitrix/install`, `/app`, `/event`.
Единственное доказательство запроса — обмен refresh-токена на `oauth.bitrix.info` с нашим
`client_secret`; идентификатор портала и адрес его REST берутся из ответа Б24, а не из тела запроса.

Что происходит при установке (`smb-bitrix-launch.service.ts`, метод `install`):

1. Проверяется, что устанавливает администратор портала.
2. Портал записывается в `smb.bitrixPortal`.
3. Если включено `SMB_BITRIX_AUTO_PROVISION_WORKSPACE`, создаётся компания: аккаунт установившего,
   workspace с сабдоменом из домена портала (`acme.bitrix24.ru` → `acme`), активация workspace
   (она же создаёт схему компании в базе). Используются штатные `signUpOnNewWorkspace` и
   `activateWorkspace`, все ограничения ядра действуют.
4. Домену портала разрешается встраивать workspace во фрейм.
5. В фоне читается список активных сотрудников портала, каждому создаётся аккаунт. Кого не успели
   создать, тот создаётся при первом открытии приложения.

Что нужно на сервере, чтобы шаг 3 сработал:

| Условие | Где задаётся |
|---|---|
| `SMB_BITRIX_CLIENT_ID`, `SMB_BITRIX_CLIENT_SECRET` тиражного приложения | `.env` |
| `SMB_BITRIX_AUTO_PROVISION_WORKSPACE=true` | `.env` |
| `IS_WORKSPACE_CREATION_LIMITED_TO_SERVER_ADMINS=false` | `.env`; по умолчанию `true`, и тогда ядро отказывает установившему, потому что он не администратор сервера. Исключение — самая первая компания на пустом сервере |
| `IS_MULTIWORKSPACE_ENABLED=true` | уже стоит в compose |
| DNS `*.<корень>` указывает на сервер, сертификат выдаётся на любой сабдомен | DNS-провайдер и Caddy; сейчас в `Caddyfile` список хостов явный |
| На сервере меньше 5 компаний | лимит ядра |

Снятие ограничения в третьей строке открывает создание компаний и на публичной странице
регистрации. Это решение владельца на каждый сервер, поэтому в `.env.example` строка закомментирована.

Если автоматическое создание выключено или не удалось, портал остаётся в статусе `PENDING` с
причиной в `lastError`, а оператор привязывает его к компании:

```bash
node dist/command/command smb:bitrix:bind-portal --member-id <id портала> --workspace-id <uuid>
```

Ограничения канала: сотрудник без email в профиле Б24 не войдёт; аккаунт, который уже состоит в
другой компании, автоматически не привязывается (проект ручной привязки — в ADR-015); во фрейме
сессия держится на cookie `SameSite=None; Secure; Partitioned`, и это надо проверить в Chrome,
Safari и Firefox на живом портале.

## 6. Как развернуть на сервере

Подробно — [`ops/deploy.md`](ops/deploy.md). Коротко: сервер получает готовый образ из GHCR
(его собирает `fork-release` после зелёного `fork-ci` на `main`), рядом лежат
`smb/deploy/docker-compose.yml`, `.env` и Caddy. Миграции Twenty и миграции форка применяются при
старте контейнера.

Локальная разработка — [`dev/local-env.md`](dev/local-env.md).
