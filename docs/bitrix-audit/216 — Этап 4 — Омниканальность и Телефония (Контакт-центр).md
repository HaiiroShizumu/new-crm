## 1. Архитектурный разбор и Поток данных (Data Flow)

### 1.1. Телефония: три стороны одной системы

```
        ┌─────────────────────┐        HTTP-коллбэки (подпись)      ┌──────────────────────┐
        │ Voximplant Cloud     │ ─────────────────────────────────► │ Портал (PHP)          │
        │ JS-сценарий:         │ ◄───────────────────────────────── │ controller_hit.php     │
        │  dial/play/gather    │      JSON с Action (Command+params)│ Routing\Router          │
        │  record/hangup       │                                    │  → ExecutionGraph      │
        └─────────────────────┘                                    │  → Call/Queue/IVR nodes│
                 │  SIP / WebRTC                                    └──────────┬─────────────┘
        ┌────────▼─────────┐                                                  │
        │ Внешние линии     │   b_voximplant_external_line / _number / _sip    ▼
        │ (провайдеры,      │                                     b_voximplant_call(+_user,
        │  номера, ACL)     │                                      _crm_entity, _queue)
        └───────────────────┘                                     → CRM (activity, lead, запись)
```

**Входящий HTTP-коллбэк** (`voximplant/controller_hit.php`, 15 КБ):
1. версия протокола по заголовку `X-Version` (1 → form-поля `$_POST`, 2 → JSON из тела);
2. подпись: `X-Request-Signature` (v2) или `BX_HASH`/`HASH` (v1);
3. `$expectedSignature === $hash` → `BX_COMMAND`/`COMMAND` (например `OutgoingRegister`, `AddCallHistory`);
4. `params = array_merge(initParams(), $params)` и диспетчеризация.

**Роутер как исполнительный граф** (`lib/routing/router.php`, 13 КБ):

```php
Router::getNextAction($request):
   $rootNode = $call->getExecutionGraph();          // сериализован в b_voximplant_call.EXECUTION_GRAPH
   if (!$rootNode) { $rootNode = $this->buildExecutionGraph($call); $call->updateExecutionGraph(...); }
   $currentNode = $this->getCurrentNode($rootNode); // по $call->getStage()
   if ($repeatedRun) { $action = $currentNode->getNextAction($call, $request); ... }
   while ($currentNode = $currentNode->getNext()) {  // защита от цикла через $seenNodes
        $this->call->updateStage($currentNode->getId());
        $action = $currentNode->getFirstAction($call);
        if ($action) return $action;
   }
   return Action::create(Command::HANGUP, ['CODE'=>500,'REASON'=>'No action found']);
```

Граф собирается по типу вызова: `buildOutgoingExecutionGraph` / `buildIncomingExecutionGraph` /
`buildCallbackExecutionGraph`, из примитивов `User`, `Queue`, `Ivr`, `Pstn`, `Voicemail`,
`SecurityCheck`, `Hangup` (каждый узел — свой файл в `lib/routing/`).
`buildQueueGraph($queueId, $checkTimeman)` **сцепляет очереди в цепочку** по `NEXT_QUEUE_ID`
(с защитой от зацикливания через `$queues[$currentQueueId]`). Результат — `Action(Command, params)`,
который облачный сценарий исполняет и возвращает следующий запрос.

**Очередь звонков** (`lib/routing/queue.php`, 4.9 КБ):

```php
[$users, $busyUsers] = $this->getUsersToInvite($queue, $call->getQueueHistory());
// ORDER: type==evenly → LAST_ACTIVITY_DATE ASC ; иначе ID ASC   (strict)

```

**Статусы вызова**: `waiting | connecting | connected | enqueued | finished` + `STAGE` (id узла графа).

## 2. Удачные решения (What to Keep / Patterns to Adopt)

### 2.1. Роутинг звонков как сериализуемый исполнительный граф
`EXECUTION_GRAPH` (узел → следующий) + `STAGE` (текущая позиция) хранятся в строке вызова.
Любой HTTP-коллбэк может продолжить выполнение с того же места без состояния на сервере между
запросами, а `getNextAction()` умеет «повторный запуск» узла (сбор DTMF) и защиту от циклов.
**Переносим:** state machine звонка = персистентный граф + курсор, идемпотентный на вход.

```text
graph = load(call.graph) ?? buildFor(call.type)          // outgoing | incoming | callback | queue-chain
node  = graph.find(call.stage) ?? graph.head
action = node.next(call, request)                        // может вернуть null → идём к graph.next
save(call.stage = node.id); return action
```

### 2.2. Правила «что делать при неответе» как данные
`NO_ANSWER_RULE ∈ {voicemail, queue, next_queue, pstn, pstn_specific, hangup}` + `NEXT_QUEUE_ID` +
`FORWARD_NUMBER` — цепочки очередей строятся в граф автоматически (с защитой от цикла).
Никакого `if/else` в бизнес-коде: новая политика = новая строка конфигурации.

### 2.3. Round-robin через «мягкую» метку активности
`LAST_ACTIVITY_DATE`/`LAST_ACTIVITY_DATE_EXACT` (микросекунды) — дешёвый и устойчивый к параллельным
запросам способ распределения: обновление метки в конце выдачи, сортировка на следующем шаге.
Никаких блокировок и «счётчиков-владений» — паттерн переносится в распределение задач.

### 2.4. Выделенная таблица таймеров сессии
`b_imopenlines_session_check` — отдельный узкий таблица с `DATE_QUEUE/DATE_NO_ANSWER/DATE_CLOSE`
и индексами по каждому дедлайну. Агенты читают её индексно, не трогая «тяжёлую» таблицу сессий.
Классический приём для любых SLA/дедлайнов: **hot deadlines — в отдельной таблице**.

### 2.5. Блокировка создания CRM-лида на вызов
```php
$lockName = self::CRM_LEAD_LOCK_NAME_PREFIX . $callId;   // vi_crm_helper.php:640
```
Адвисори-лок по `callId` не даёт параллельным коллбэкам создать два лида на один вызов
(типичная гонка «два webhook'а пришли одновременно»). Плюс результат инкапсулирован в `Result`
с кодами исхода (`CRM_LEAD_OUTCOME_NOT_REQUIRED`…).

### 2.6. SSRF-защита при скачивании записей (высший класс)
`lib/security/PublicUrlValidator` (по комментариям — свежая, осознанная разработка):
* схема только `http/https`, пустой хост → отказ;
* IDN → punycode перед DNS;
* `collectAddresses()` → проверка, что **все** адреса глобально маршрутизируемы (`isGloballyRoutable`);
* fail-closed: не разрешён хост → запрос не выполняется, код ошибки `PRIVATE_IP`;
* не разрешается хост → временный код `SERVER_NOT_AVAILABLE` (ретраи без нарушения инварианта);
* **на выходе — IP для пиннинга соединения** (`Data: ['ip']`), чтобы второй (непроверенный) DNS-резолв
  не обнулил защиту (DNS rebinding);
* `RecordDownloader` закрепляет IP (`setPinnedIp`) и переопределяет `checkRequest()`.

Это готовый шаблон безопасного server-side fetch для любой системы.

### 2.7. Строго типизированный контракт события-хука
`sendEventOnBeforeSessionTransfer()` проверяет ответ обработчика по семи полям
(`RESULT` bool, `OPERATOR_ID` число или `queue<N>`, `OPERATOR_LIST` массив чисел,
`DATE_QUEUE` DateTime|false, `QUEUE_HISTORY` массив) и при ошибке шлёт
`OnErrorEventBeforeSessionTransfer` с перечнем нарушений, а не молча ломает передачу.
Обработчики расширения получают валидируемый контракт — редкость для Bitrix-событий.

### 2.8. Инкрементальные агенты с режимами запуска
`agent.php`: `transferToNextInQueue($nextExec, $offset)`, `closeByTime`, `mailByTime` — со смещением
и возвратом строки для перепланирования; `isCronCall/isExecModeAgent/isExecModeCron` — один код
работает и в «Агентах Битрикс», и в cron. Плюс само-перепланирование push-подобных задач (этап 3).

### 2.9. RBAC по линиям и номерам
`b_voximplant_role/_role_permission/_role_access` + `b_voximplant_line_access` + `blacklist` +
`accesscodefilter` — телефония ограничивается отдельными ролями (кто может звонить на номер,
кто слушает записи), а не глобальными правами CRM.

## 3. Антипаттерны и Архитектурные тупики (What NOT to Do)

### 3.1. God-config и God-session
* `b_imopenlines_config` — **одна строка = вся настройка линии** (80+ колонок: CRM, очередь, боты,
  рабочее время, автозакрытие, голосование, категории). Добавление любой фичи — ALTER TABLE +
  ещё одна колонка `*_TEXT/ENABLE/RULE/FORM_ID/BOT_ID`.
* `b_imopenlines_session` — ~70 колонок, включая 4 CRM-флага (`CRM_CREATE_LEAD/COMPANY/CONTACT/DEAL`),
  5 таймингов, `EXTRA_*` под каждый внешний канал и `QUEUE_HISTORY` как сериализованный текст.

Следствие: ни одну из этих таблиц нельзя спроектировать заново; миграции — по одной колонке;
любая выборка «сессии с фильтрами» перечисляет десятки полей.

### 3.2. Конфигурация в колонках вместо JSONB/справочника
Пара `*_RULE + *_FORM_ID + *_BOT_ID + *_TEXT` повторяется **минимум 6 раз** в одном конфиге
(`NO_ANSWER`, `WORKTIME_DAYOFF`, `CLOSE`, `AUTO_CLOSE`, `VOTE_1`, `VOTE_2`). Это скрытый
дочерний справочник, размазанный по колонкам: добавить второй сценарий голосования или
второй язык нельзя без миграции.

### 3.3. Сериализованные массивы в текстовых колонках
`QUEUE_HISTORY text` (в `b_imopenlines_session`), `EXECUTION_GRAPH text`, `QUEUE_HISTORY text`
(в `b_voximplant_call`), `CRM_BINDINGS text`, `SIP_HEADERS text`, `CALLBACK_PARAMETERS text`.
Нельзя запросить «показать сессии, где оператор X уже был» без `LIKE`/полной выгрузки;
нельзя составным индексом покрыть; целостность не проверяется.

### 3.4. Дублирование трёх систем очередей
Очередь звонков (`voximplant/routing/queue.php`), очередь диалогов (`imopenlines/queue/*`) и
«внутренняя» очередь уведомлений (`imopenlines/lib/im/messages/queue.php`) реализуют одинаковую
семантику (доступные участники → исключение уже обслуженных → правило при отсутствии) тремя
независимыми кодами с разными типами правил. Единый `DispatchPolicy` покрыл бы обе предметные области.

### 3.5. Логика, завязанная на строковые константы-«магию»
`'evenly'|'strictly'|'all'`, `'none'|'text'|'form'|'bot'`, `'voicemail'|'queue'|'next_queue'|'pstn'`,
`STATUS_*` числа `0..75` со «свободными» промежутками (5, 20, 25, 40, 50, 60, 65, 69, 75).
Нет enum/классов-типов (кроме V2-направления), сравнения размазаны по коду
(`(string)$this->session['STATUS']`, `(int)$this->config['...']`).

### 3.6. Сравнение массива с числом в стратегии evenly
```php
if ($operators[$operatorId] > 0)   // $operators[$operatorId] — массив строки результата
{
    QueueTable::update($operators[$operatorId]['ID'], [...]);
}
```
(`lib/queue/evenly.php`). Работает **случайно**: в PHP массив всегда «больше» числа, а при отсутствии
ключа `null > 0` = false. Под `strict_types`/PHP 9 и при смене структуры — молчаливая поломка
round-robin. Классический пример «код проходит тесты не потому, что верен».

### 3.7. Агенты, читающие «всё подряд» с offset

## 4. Анализ безопасности и Уязвимостей (Security Audit)

### 4.1. Подпись webhook'ов: md5, без nonce и времени
```php
// vi_http.php:1209
public static function RequestSign($type, $str) {
    if ($type == self::TYPE_BITRIX24 && function_exists('bx_sign')) return bx_sign($str);
    include($_SERVER['DOCUMENT_ROOT']."/bitrix/license_key.php");
    return md5($str.md5($LICENSE_KEY));       // ключ — лицензионный файл
}
// CheckDirectRequest():  md5($rawRequest . "|" . GetPortalSign())
```
и сравнение `$expectedSignature === $hash` в `controller_hit.php`.

Находки:
1. **md5 как основа MAC** — не collision-resistant; для подписи webhook это минимум legacy-уровень.
2. **Нет timestamp/nonce** → перехваченное тело можно переигрывать бесконечно (replay).
   Для команд вроде `AddCallHistory` это = повторное создание истории/лидов.
3. **Сравнение через `===`**, а не `hash_equals()` → timing side-channel (второстепенно, но дёшево исправить).
4. **Канонизация подписи** — `implode("|", $params)`: при вложенных массивах PHP подставит `"Array"`,
   порядок ключей не нормализуется → подпись зависит от порядка/типов и может быть воспроизведена
   по-разному для одного и того же события.

**Фикс:** `HMAC-SHA256(canonical_json(body), secret)` + заголовки `X-Timestamp` (окно ±5 мин) +
одноразовый `X-Nonce` в Redis с TTL.

### 4.2. IDOR на канал/источник в параметрах
В `controller_hit.php` параметры из запроса (`CALL_ID`, `PHONE_NUMBER`, `ACCOUNT_SEARCH_ID`,
`CRM_BINDINGS`, `USER_ID`) используются после проверки подписи — подписанный источник допустим.
Но `ACCOUNT_SEARCH_ID` **перетирает** `PHONE_NUMBER` (`$params['PHONE_NUMBER'] = $params['ACCOUNT_SEARCH_ID']`)
до обработки — любой подписанный вызов может подменить номер, по которому идёт поиск контакта.
**Требует проверки:** доверие к `ACCOUNT_SEARCH_ID` и последствия для привязки к CRM.

### 4.3. Доступ к записям звонков
`DownloadAgent()` берёт `CALL_RECORD_URL` (или base64-decode из параметров) и качает его.
Современный путь защищён `PublicUrlValidator` + IP-pinning (§2.6 — позитив). **Но:**
`$recordUrl = base64_decode($recordUrl)` из внешнего входа — любой, кто может отправить задачу агенту
с произвольным URL, проверяется только валидатором; старый путь (`vi_history.php`) и ручные вызовы
могут миновать валидацию. Нужна единственная точка входа для скачивания.

### 4.4. Обходы проверок в диспетчеризации
* `IMOL\Debug::addQueue` — пишет параметры сессий в лог (включая `OPERATOR_ID`, причины) без
  маскирования — доступ к логу = информация о клиентах.
* `SKIP_CONNECTOR => 'Y'`, `SKIP_COMMAND => 'Y'` — пропуск шагов обработки по флагам (та же болезнь
  `disableCheckAccess`, этап 2).
* `Chat::transfer([... 'TO' => 0])` — «передача в никуда» при пустой очереди: сессия остаётся
  `UNDISTRIBUTED='Y'` до часа (`QUEUE_TIME` default 60 с, `UNDISTRIBUTED_QUEUE_TIME = 3600`).

### 4.5. Гонки при распределении
Две параллельные сессии могут получить одного и того же оператора: проверка
`getCountFreeSlotOperator()` и последующее назначение **не в одной транзакции**.
Защита есть только на уровне чата (`Lock` на `imol_transfer_chat_id_<chatId>`), но не на уровне
«оператор + слот». При `MAX_CHAT=3` под нагрузкой возможен перевыброс — т.е. классическая
TOCTOU-гонка. Фикс: атомарный `UPDATE … WHERE free_slots > 0` или `SEL​ECT FOR UPDATE SKIP LOCKED`
по строке оператора в `b_imopenlines_queue`.

### 4.6. Что проверено и что нет
Подтверждено чтением кода: подписи webhook'ов и их состав, отсутствие replay-защиты, SSRF-валидатор
и пиннинг IP, лок на создание лида, отсутствие транзакции в диспетчеризации, `QUEUE_HISTORY` в тексте,
сравнение массива с числом в evenly, лимиты и правила очередей, схемы 25+30 таблиц.
**Не проверено экспериментом:** достижимость replay на `controller_hit`, обход `PublicUrlValidator`
через альтернативные DNS/прокси, фактическое перевыброс слотов при параллельных сессиях,
доступность `b_imopenlines_log` для рядовых пользователей.

### 5.2. Движок распределения (единый для звонков и диалогов)

```go
// DispatchPolicy — одна абстракция на обе предметные области (паттерн §3.4)
type Strategy interface {
    // кандидаты уже отфильтрованы: active, not in history, slots free, in worktime
    Pick(ctx, req PickRequest) (Decision, error)
}

// round_robin: UPDATE ... SE​T last_served_seq = nextval() WHERE ... RETURNING  (атомарно!)
// broadcast  : вернуть всех кандидатов (чат становится групповым)
// strict     : первый по priority, исключая operator_history
```
Распределение — **одна атомарная операция** (паттерн к §2.5):
```sql
UPDATE line_operator
SE​T    active_chats = active_chats + 1,
       last_served_at = now(), last_served_seq = nextval('dispatch_seq')
WHERE  line_id = $1 AND active_chats < max_chats AND status = 'online'
  AND  NOT ($2 = ANY($line_session.operator_history))
ORDER BY last_served_seq ASC
LIMIT  1
RETURNING user_id;
```
Вернула строку → слот занят атомарно, гонки нет. Откат при отказе клиента подключиться —
`active_chats - 1` в транзакции/по событию.

### 5.3. Схема фоновых воркеров

| Воркер | Технология | Задача |
|---|---|---|
| `deadline-worker` | Go, `SELECT … FOR UPDATE SKIP LOCKED FR​OM session_deadline WHERE fire_at <= now()` | no_answer, auto_close, vote, mail — паттерн таблицы таймеров |
| `telephony-webhook` | HTTP-сервис | приём колбэков провайдера: HMAC + timestamp + nonce, идемпотентность по `(provider, provider_call_id)` |
| `call-recorder` | worker с ретраями | скачивание записи: **только** `SafeFetcher` (валидация + IP-pinning, §2.6) |
| `line-stat-aggregator` | consumer | метрики SLA (первый ответ, время в очереди) → аналитика |
| `session-close-projector` | consumer | закрытие → создание/обновление CRM-сущности через outbox (этап 2) |
| `queue-reconciler` | периодическая | сверка `active_chats` с фактическими открытыми сессиями (лечит рассинхрон) |

### 5.5. Матрица замен

| Велосипед Bitrix (этап 4) | Замена |
|---|---|
| `EXECUTION_GRAPH text` + `STAGE varchar` | граф состояния в `flow_state JSONB` + версия схемы; переходы — чистая функция |
| md5-подпись webhook без времени | HMAC-SHA256 + `X-Timestamp` (±5 мин) + nonce в Redis |
| `QUEUE_HISTORY text` | `operator_history BIGINT[]` (GIN) — запросы без `LIKE` |
| `b_imopenlines_config` на 80 колонок | `line.routing/ sla/ crm JSONB` + JSON-схема валидации |
| 3 независимые реализации очередей | единый `DispatchPolicy` + стратегии |
| `getCountFreeSlotOperator` + отдельный UPDATE | атомарный `UPDATE … RETURNING` (нет TOCTOU) |
| md5/`===` сравнение | `hash_equals()` везде |
| `PublicUrlValidator` (voximplant) | **переносится как есть** — общий `SafeFetcher` для всех download-операций |
| `session_check` с таймерами | `session_deadline` (тот же удачный паттерн, обобщённый) |
| агенты «offset/LIMIT» | очередь с `SKIP LOCKED` и курсором по PK |
| `CRM_LEAD_LOCK_NAME_PREFIX` | то же: идемпотентный ключ по `provider_call_id` в unique-индексе |
| логи в 4 разных таблицах | единый structured log с `trace_id` (OpenTelemetry) |

### 5.6. Чек-лист этапа 4

1. Весь вход от провайдеров — подписанный, с временем, nonce и идемпотентным ключом.
2. Распределение — одна атомарная операция; слоты нельзя «взять» дважды.
3. Дедлайны — в отдельной таблице с индексом по `fire_at`, обработка через `SKIP LOCKED`.
4. Конфигурация линии — документ с JSON-схемой, не 80 колонок.
5. Скачивание внешних URL — через единый валидатор с IP-пиннингом.
6. Статусы — enum, переходы — функция, «чинилки» статусов запрещены.
7. Очереди звонков и диалогов — одна абстракция, две стратегии-конфигурации.
8. Хаки под конкретные мессенджеры — только в адаптерах коннекторов.
