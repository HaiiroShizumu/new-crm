## 2. What to Keep / Patterns to Adopt

1. **Checkpoint состояния процесса = один BLOB + оптимистичный захват.** Весь граф сериализуется
   (`workflowpersister.php:290-297`), строка инстанса захватывается `OWNER_ID/OWNED_UNTIL` + адвисори-локом
   (`workflowpersister.php:390-401`), конфликт = 423, ретраи агентом 1/5/10 мин (`schedulerservice.php:665-673`).
   Паттерн дёшев (одна строка на инстанс), устойчив к параллельным агентам и не требует блокировок на
   уровне бизнес-данных. Псевдокод:
   ```
   lock = acquire(INSTANCE, owner_id, until=now+ttl)      -- SELE​CT … FOR UPDATE / GET_LOCK
   if (!lock) return RETRY(1m, 5m, 10m)                   -- отдельная очередь, не веб-запрос
   state = unserialize(gunzip(WORKFLOW))                  -- allowed_classes = allowlist активностей
   runQueue(); save(gz(serialize(state)), owner_id=me)
   ```
2. **Явный конвейер обновления сущности** как в tasks (`UpdateService.php:81-212`): validate → save →
   history → search index → event → cache → counters → push. Каждый шаг именован и тестируем; порядок
   (история до события, кэш после сохранения) — это и есть бизнес-инвариант. Копировать как application-service.
3. **Append-only журнал событий с причиной.** `b_tasks_log (FIELD, FROM_VALUE, TO_VALUE)`
   (`install.sql:178-189`) и `b_timeman_work_time_event_log (EVENT_TYPE, ACTUAL_TIMESTAMP, REASON)`
   (`:203-215`) дают аудит и возможность пересчитать агрегат. Для CRM — тот же принцип: агрегаты
   восстанавливаются из журнала.
4. **Декларативные миграции одним билдером** — `install/migrations/tables.php` + `CreateTableBuilder`
   (bizproc: 61 таблица в одном файле, DDL генерируется единообразно, `CREATE TABLE IF NOT EXISTS` —
   `main/lib/db/mysqlcommonconnection.php:104`). Один файл = обзор всей схемы, версионируется в git.
5. **«Таблица-очередь + агент/степпер» вместо кронов.** `b_bp_script_queue` + `Stepper`
   (`lib/script/queue/stepper.php:27-64`) обрабатывают по одному документу за прогон, с проверкой прав
   перед стартом (`:84`); у сообщений есть `TTL/AVAILABLE_AT/STATUS` (`tables.php:671/687`).
   Идемпотентность и backoff встроены в топологию.
6. **Прочитанность без денормализации.** `COUNT(DISTINCT …)` по PK-таблице просмотров
   (`comments/task.php:42-63`) против «счётчик в строке задачи»: нет рассинхрона, запрос дешевле, чем
   кажется, при индексе `(TASK_ID, USER_ID)`.
7. **Ограничение «один активный таймер» через PK.** `b_tasks_timer PRIMARY KEY (USER_ID)`
   (`install.sql:293-300`) — целостность на уровне схемы, а не приложения (единственный такой случай в
   рассмотренных модулях — и он же правильный).
8. **Подписи параметров и allowlist unserialize.** Параметры документа подписываются
   `Main\Security\Sign\Signer` (`document.php:1814-1857`), `unserialize` — только с собранным allowlist
   активностей (`runtime.php:892-933`) либо `allowed_classes => false` (`workflowtemplate.php:210`).

## 3. What NOT to Do / Architectural Dead Ends

1. **Синхронная тяжёлая работа внутри веб-запроса.** `autoStartWorkflows()` гоняет N шаблонов
   `CreateWorkflow()+Start()` в текущем запросе (`document.php:552-587`); `sendEventsInternal()` синхронно
   обходит все подписки (`schedulerservice.php:416-540`); каждый комментарий синхронно делает денормализующий
   `UPDATE b_tasks SE​T ACTIVITY_DATE` (`comment.php:625`). Механизм дорогого: время ответа растёт линейно
   от числа процессов/подписок, всё упирается в один PHP-FPM worker. В своей CRM — никогда: старт процесса
   только через очередь.
2. **N+1 вместо агрегатов.** Список задач выполняет 2 correlated `SUM()`-подзапроса **на строку**
   (`taskprovider.php:322-324`); `setState()` делает `DELETE` прав, затем `INSERT` по строке в цикле
   (`stateservice.php:588-603`); `CBPTaskService::add()` — `INSERT` на каждого пользователя (`taskservice.php:700-710`).
   Масштабируется O(users×tasks) в одном запросе.
3. **Три параллельные модели одной связи.** «Документ → workflow» хранится в `b_bp_workflow_state`,
   `b_bp_workflow_instance` и `b_bp_workflow_filter` — все три по `DOCUMENT_ID/ENTITY/MODULE_ID`
   (`tables.php:38,69,406`), синхронизируются ручным `syncStatus()` (`workflow.php:1518`). Одна пара
   (FK-less) уже не защищена, три — источник расхождений.
4. **`eval` как механизм исполнения.** Агенты (`agent.php:507-508`), генерация `EO_*` (`Entity.php:988`),
   «PHP-код» в процессах `@eval($expression)` (`EvalService.php:11-25`) — компрометация любой строки в `b_agent`
   или шаблона = RCE. В коробке CodeActivity разрешён, в облаке выключен фильтром
   (`activities/bitrix/codeactivity/.description.php`, `CBPHelper::DISTR_B24`, `helper.php:16`).
5. **SQL-конкатенация вместо параметров.** `IN (".implode(",", $ids).")"` (`stateservice.php:540`),
   `WS.ID IN (".implode(',',$workflowId).")"` (`stateservice.php:285`), raw `INSERT IGNORE`
   (`createuserfilterstepper.php:60`), `DELETE FR​OM b_module_to_module WH​ERE … forSql(...)` (`EventManager.php:143-153`).
   Значения сегодня `intval`/`forSql` — но это конвенция, а не гарантия.
6. **Права по умолчанию «разрешено».** `canOperate()` возвращает `true`, если указанные состояния
   «не релевантны» стейт-машине (`document.php:329-340`), `getAllowableOperations` = `null` без
   `STATE_PERMISSIONS` (`:279`); `DataManager::setDefaultScope` — no-op (`DataManager.php:304-307`).
   Проверка прав — opt-in: забыл вызвать = дыра.
7. **Схема без FK и триггеров (0 во всех модулях) + гонки на чтении.** В timeman нет UNIQUE на активную
   запись (`install.sql:41`), `findLatestRecord()`/`findOverlappingRecordByDates()` — просто SELE​CT в
   приложении (`worktimerepository.php:206,228`): два параллельных старта дают две `OPENED`-записи,
   транзакция блокировок не добавляет. Целостность «на if-ах» ломается ровно под параллельностью.
8. **Два источника истины о схеме** (DDL в `tables.php` vs map в PHP-классе, §1.1) и синхронные события
   как шина по умолчанию (`EventManager.php:370-376`, исключение в release гасится) — связность,
   которую трудно локализовать при рефакторинге.
9. **Синглтоны и service locator как глобальное состояние**: `Application::getInstance()`
   (`Application.php:104-110`), `EventManager::getInstance()` (`EventManager.php:32-41`), `global $DB, $APPLICATION`
   (`agent.php:31,366`) — тесты и конкурентность держатся на дисциплине, а не на архитектуре.

## 4. Security Audit

### 4.1 Исполнение кода (код-верифицировано)
- `eval` строки агента: `agent.php:507-508`; запись в `b_agent.NAME` делает `CAgent::AddAgent` (`agent.php:91`).
  Доступ к ALTER таблицы = RCE; поверхность — любая SQL-инъекция или админ-интеграция.
- `EvalService::evaluate()` = `@eval($expression)` (`bizproc/lib/Internal/Service/EvalService.php:11-25`)
  — исполняет выражения шаблонов и генерит классы REST-роботов (`:45`). CodeActivity в коробке разрешён.
- `unserialize` в bizproc: местами строгий allowlist (`runtime.php:892-933`), местами
  `allowed_classes => false` (`workflowtemplate.php:210`, `taskservice.php:1101`) — инвариант «всегда strict»
  держится на аккуратности автора.

### 4.2 Проверки прав и IDOR (код-верифицировано; эксперимент нужен для эксплуатации)
- Комментарии: `ACTION_TASK_READ` проверяется **только если пользователь не автор** комментария
  (`commentitem.php:57-64`); ветка автора упирается в `TaskEntity::canAdd` — обрыв этой ветки = чтение/запись
  чужого топика. Три разных правила правки (админ `taskentity.php:76-91`, опция `:58`, «только последний»
  `taskcomments.php:440-453`) — их легко перепутать при клонировании логики.
- timeman: use-cases старта/стопа/паузы проверяют только `canManageWorktime()` и **не сверяют `$userId` с
  текущим пользователем** (все `usecase/worktime/manage/*/handler.php`; `permissions.php:50` — операция
  включена в роль по умолчанию); `changeRecordAction` пишет правку мимо `canUpdateWorktime`
  (`lib/controller/worktime.php:151-182`).
- bizproc: `canOperate()` default-true (§3, п. 6), `canUserOperateDocument()` вызывается степпером явно
  (`stepper.php:84`) — но только там.

### 4.3 Гонки (код-верифицировано, эксплуатация не воспроизводилась)
