### 2.2. Декларативные дескрипторы полей
`Factory::getFieldsSettings()` — чистые массивы-описания:

```php
Item::FIELD_NAME_TITLE => ['TYPE' => Field::TYPE_STRING,
                           'ATTRIBUTES' => [CCrmFieldInfoAttr::HasDefaultValue, CCrmFieldInfoAttr::CanNotBeEmptied],
                           'CLASS' => Field\Title::class],
Item::FIELD_NAME_STAGE_ID => ['TYPE' => Field::TYPE_CRM_STATUS, 'CRM_STATUS_TYPE' => $this->getStagesEntityId()],
```
из них собирается `Field\Collection` (итератор + ArrayAccess) и `Item\DisabledField` для capability-ограничений.
Одна декларация обслуживает: валидацию, форму, список, фильтр, REST, документ-генерацию.
**Это лучшая часть ядра** — в новой системе: реестр полей = конфиг с типами/атрибутами/валидаторами,
один раз читается в codegen/OpenAPI.

### 2.3. Operation как именованный сценарий с явным pipeline
`Operation::launch()` — последовательность именованных шагов с точками отказа и агрегацией ошибок
(`mergeResults`), а не «сохрани и надейся». Плюс `TransactionWrapper`, который делает **правильный
порядок**: вся запись в транзакции, а side-effect'ы (bizproc, automation) — после COMMIT:

```php
$this->operation->disableBizProc()->disableAutomation();
$this->connection->startTransaction();
$result = $this->operation->launch();
$result->isSuccess() ? commit : rollback;
if ($isBizProcEnabled)    $this->runBizProc();
if ($isAutomationEnabled) $this->runAutomation();
```
**Переносим дословно**: `command → transaction → outbox → post-commit handlers`.

### 2.4. Стадии как данные с инвариантами в слое добавления
Одна таблица `b_crm_status` на все сущности; семантика (`P/S/F`) и запрет «второго успеха»
проверяются в `StatusTable::onBeforeAdd/onBeforeUpdate`, кэш стадий — per-`ENTITY_ID`
(`getStatusesByEntityId` → `static::$statusesCache`). Идентификатор стадии несёт категорию
(`C5:PREPAYMENT_INVOICE`), поэтому воронки не требуют отдельного справочника переходов.

### 2.5. Capability-флаги в конфигурации типа, а не в коде
19 колонок `IS_*_ENABLED` в `b_crm_dynamic_type` + методы `Factory::isXEnabled()` — тип сам
декларирует, что поддерживает. `Item` при сборке получает `DisabledField` и молча не предлагает
то, чего нет. Это даёт возможность иметь «сделку без продуктов» и «смарт-процесс с воронками»
без форка кода.

### 2.6. Батчинг в таймлайне (защита от N+1)
`TimelineManager::prepareDisplayData()` сначала строит `$entityMap[type][id] = [ITEM_IDS]`,
затем для каждого типа делает **одну** выборку на все id (`CCrmActivity::GetList(['@ID'=>…])`,
`NoteTable::loadForItems`, `prepareAuthorInfoBulk` c `$userMap`). Модель «сгруппируй → загрузи
по типу → разложи обратно» — правильный шаблон для любых связанных данных.

### 2.7. Денормализованный поисковый слой
`SEARCH_CONTENT MEDIUMTEXT` + FULLTEXT-индекс в каждой основной сущности + отдельная
`b_crm_timeline_search` на владельца таймлайна. Полнотекст не просчитывается на лету в основном
запросе, пишется в том же цикле сохранения.

### 2.8. Корзина как «переезд», а как флаг
`Recycling\BaseController` при удалении **перебиндит** сущность в suspended-тип и переносит
связанные подсистемы наборами `suspend*/recover*/erase*`: timeline, livefeed, UTM, tracing,
документы, пользовательские поля, workflow. Плюс `lockItem/unlockItem` (advisory-lock) против
параллельного восстановления. Идея «удаление = согласованная миграция всех зависимых записей»
переносима; исполнение — нет (см. §3.9).

### 2.9. Capability-обнаружение вместо исключений в горячем пути
`Factory::getItemsCount()` начинается с `isTableExists($tableName) → return 0`. Неприятно для
производительности (см. §3.8), но это осознанная «мягкая деградация», а не fatal. В новой системе
такие проверки должны выноситься в момент провизионирования, а не выборки.

## 3. Антипаттерны и Архитектурные тупики (What NOT to Do)

### 3.1. God-Container и God-Factory
* `Service\Container` — **сервис-локатор: 80 геттеров `get*` из 85 методов**, каждый возвращает свой синглтон.
  Зависимости не видны в сигнатуре, тест требует полного контейнера, циклы находятся в рантайме.
* `Service\Factory` — **2 394 строки / 130 методов**: метаданные полей + категории +
  стадии + операции + capability-флаги + подсчёты + права. Наследники добавляют ещё.
* 29 методов вида `is*Enabled()` — перечисление продуктовых флагов прямо в базовом классе.

**Вывод:** разбить на `FieldCatalog`, `CategoryService`, `StageService`, `OperationFactory`,
`CapabilitySet` (значение, а не 19 геттеров), `EntityQueryService`.

### 3.2. Flag-soup: 31 метод `enable*/disable*` на операцию (105 методов всего)
`Operation.php` (1 552 строки) содержит `enableCheckAccess/disableCheckAccess/disableAllChecks/enableBizProc/
disableAutomation/enableSaveToHistory/enableCheckLimits/…` (строки 790–1060). Конфигурация
поведения — это мутабельное состояние объекта, выставленное вызывающим кодом **до** `launch()`.
Ошибка в одном месте тихо отключает проверку прав или историю.

### 3.3. `Item::save()` — «не зовите, сломаете систему» вместо инкапсуляции
```php
/**
 * @internal DON'T CALL THIS METHOD DIRECTLY!!! Use Operations!
 * ... Calling it directly leads to inconsistent state of the system.
 */
public function save(bool $isCheckUserFields = true): Result
```
Когда единственный безопасный путь — это пометка в docblock, инвариант не защищён.
Одновременно `Item` (2 459 строк / 63 КБ, 108 методов) — «бог»: поля всех сущностей, `__call`-магия, `ArrayAccess`,
`JsonSerializable`, наблюдатели, продуктовые строки, UTM, коллекции. Плюс
`$this->itemBeforeSave = clone $this->item` — поверхностное клонирование ORM-объекта
(общие ссылки на `entityObject`/коллекции).

### 3.4. `CCrmOwnerType` — 3 990 строк магических чисел и двух схем кодирования
```php
Lead=1, Deal=2, … SuspendedLead=18 … SmartB2eDocument=39, SuspendedSmartB2eDocument=40
DynamicTypeStart=128, DynamicTypeEnd=192, SuspendedDynamicTypeStart=192, SuspendedDynamicTypeEnd=256
UnlimitedTypeStart=1030   // дальше suspended кодируется ЧЁТНОСТЬЮ: активен — чётный, корзина — нечётный
```
Смещение для статических типов = +17, для динамических = +64, для `>=1030` = +1 по паритету.
Найден конкретный баг копипасты (`crm_owner_type.php:575–630`):

```php
case self::SmartB2eDocument:
case self::SuspendedSmartB2eDocument:
    return self::SuspendedSmartDocument;   // 37 вместо 40
```
**Урок:** идентичность сущности должна быть строковым кодом (`deal`, `smart:128`),
сuspended — состояние записи (`deleted_at`), а не отдельный числовой тип.

### 3.5. Три механизма хранения полей одновременно
Колонки основной таблицы + `b_uts_*` (EAV-колонки) + `b_utm_*` (EAV-строки) + `b_crm_field_multi`
(третий EAV для мультизначных) + `b_user_field` (метаданные). Следствия:
* фильтр по полю должен знать, в каком из четырёх мест оно лежит (`Factory::prepareFilter`,
  `Field\*`, `UserFieldFilterable`, `crm/filter/*` — 47 файлов провайдеров фильтров);
* сортировка/агрегация по пользовательскому полю почти всегда отдельный спец-код;
* `b_crm_requisite` получил **48 индексов** — прямое следствие «индексируй то, что не спроектировано».

### 3.6. Runtime-DDL в продуктовом коде
* `ALTER TABLE b_uts_* ADD <field>` при создании поля (см. §1.2);
* `CREATE TABLE` для смарт-процесса/индекса/ACL-таблицы из ORM-события `onAfterAdd`;
* `dropTable()` «незавершённого» типа прямо в `onBeforeAdd`;
* `isTableExists()` в `getItemsCount()`/`getItemsOpportunityAccountAmount()`;
* отложенный `syncColumnsAgent` для выбрасывания колонок.

DDL в рантайме = блокировки метаданных, расхождения схем между узлами, невозможность отката,
невозможность review. В новой системе: пользовательские поля — JSONB/отдельная таблица значений;
создание «типа сущности» — миграция через Change-Data-Capture каталога, а не SQL из веб-запроса.

### 3.7. Недетерминированная транзакционность
Один и тот же `Operation::launch()` выполняется **в транзакции** (autorun-контроллеры) и
**без транзакции** (REST/компоненты/агенты, кто вызвал напрямую). Значит, поведение при ошибке
на 5-м шаге пайплайна зависит от вызывающего: где-то откатится всё, где-то останутся
обновлённые права и поисковый индекс без записи сущности. Плюс `runBizProc()/runAutomation()`
**скопированы** в `TransactionWrapper` с пометками `@see Operation::runBizProc() - copy-paste`.

### 3.8. «Костыльные» индексы вместо спроектированных выборок
Замер: **702 индекса на 258 таблиц** crm; `b_crm_requisite` — 48, `b_crm_deal` — 22,
`b_crm_lead` — 21, `b_crm_act` — 20. Пример — пять почти одинаковых составных индексов сделки:

```
IX_DEAL_26 (STAGE_SEMANTIC_ID, CATEGORY_ID, STAGE_ID)
IX_DEAL_31 (CATEGORY_ID, STAGE_ID, IS_RECURRING)
IX_DEAL_33 (STAGE_ID, CATEGORY_ID, STAGE_SEMANTIC_ID)
IX_DEAL_35 (ASSIGNED_BY_ID, STAGE_SEMANTIC_ID, CATEGORY_ID, IS_RECURRING)
IX_DEAL_36 (BEGINDATE, STAGE_SEMANTIC_ID)
```
Каждый добавлен под конкретный отчёт/фильтр → write-amplification на каждое сохранение сделки
(22 индекса переписываются), планы запросов дробятся, статистика «протухает».

### 3.9. Корзина удаления = 15 синхронных операций без единого описания
`BaseController` (26 КБ) — наборы `suspend*/recover*/erase*` для timeline, livefeed, UTM,
tracing, документов, UF, workflow + `transformUserFields` + `synchronizeTimeline` + события.
Пара «удалить/восстановить» написана вручную для каждой подсистемы; пропуск одного шага =
осиротевшая запись. Правильная модель — outbox-событие `entity.deleted`, на которое каждая
подсистема подписана сама.

### 3.10. Свитч-цепочка вместо реестра
`TimelineManager::resolveController()` — 18 последовательных `elseif` (плюс ветки по `TYPE_ID`)
по `TYPE_ID` и `ASSOCIATED_ENTITY_TYPE_ID` (`timelinemanager.php:16–140`), включая загрузку классов через
`class_exists` по строке. Добавление типа = правка центрального метода (нарушение открытости-закрытости),
а `DynamicController::getInstance($assocEntityTypeID)` ветвится последним — приоритеты неявны.

### 3.11. Миграции, включённые опциями
`Repository::hasFieldsContextTables()` → `Option::get('crm','crm_fields_context_dynamic_tables_created','Y') === 'Y'`;
`ConditionBuilder` → опция `CRM_MOVE_OBSERVERS_TO_ACCESS_ATTR_IN_WORK`; `AttrConvertOptions` —
список не-converter'нутых типов в опциях. Флаги живут годами, поведение инсталляций расходится,
и «почему у клиента иначе» становится нерешаемым вопросом.

### 3.12. Двойной проход выборки как норма
`getItems()` всегда делает 2 запроса (id → fetch) и снимает `runtime.permissions` вторым.
Это разумно против дублей от join'ов, но:
* для страницы из 50 элементов это 2 round-trip'а вместо 1;
* `unset($params['runtime']['permissions'])` — **неочевидная точка снятия прав**: любой, кто
  переиспользует `$params` позже, получает выборку без ACL-джойна.

## 4. Анализ безопасности и Уязвимостей (Security Audit)

### 4.1. Отключение проверки прав одним вызовом-флажком
`Operation::disableCheckAccess()` / `disableAllChecks()` вызывается минимум в 20 местах, включая
публичные и внешние контуры:

```
lib/webform/resultentity.php:248,743            ← публичная веб-форма
lib/integration/aiassistant/tools/userfield/edit/basesetfieldvaluetool.php:118
lib/integration/ai/operation/fillitemfieldsfromcalltranscription.php:368
lib/integration/bizproc/document/item.php:262
lib/integration/im/chat.php:179
classes/general/entity_helper.php:360           ← if (!$checkPermissions) $operation->disableCheckAccess()
lib/Service/Communication/Channel/Event/ChannelEventRegistrar.php:433,570,603
lib/Service/LastActivity.php:201, lib/Service/Integration/Sign.php:250,268
```

Корень проблемы: **нет технической гарантии, что перед снятием проверки была выполнена своя
авторизация**. Ответственность целиком на вызывающем коде, а вызывающих — десятки, в том числе
обработчики событий и AI-инструменты.

Дополнительно в веб-форме (`webform/resultentity.php:225–250`) объявлен анонимный класс-наследник
мерджера с **пустыми** заглушками проверок:

```php
protected function checkEntityReadPermission($entityID,$userPermissions){}
protected function checkEntityUpdatePermission($entityID,$userPermissions){}
protected function checkEntityDeletePermission($entityID,$userPermissions){}
...
$dynamicResult = $dynamicOperation->disableCheckAccess()->disableCheckFields()
                    ->disableBizProc()->disableAutomation()->launch();
$dynamicResult->isSuccess();   // результат никуда не передаётся
```
Строка `$dynamicResult->isSuccess();` — выражение без эффекта: ошибка записи молча теряется.

### 4.2. Контекст пользователя «по умолчанию = админ»
```php
(new Crm\Service\Context())->setUserId($this->assignedById ?: 1)   // resultentity.php:245 и :740
```
`assignedById` приходит из `onSiteFormFill` (обработчики модулей) и по умолчанию `null`.
Итог: публичная форма пишет сущность **от имени пользователя 1** (администратора) с отключённой
проверкой прав. Это сознательный service-account-паттерн, но:
* неочевиден (литерал `1` вместо явного «системного пользователя»);
* любая ошибка в обработчике `onSiteFormFill` (или его отсутствие) продолжает писать от админа;
* журнал аудита теряет реального автора (автор проставляется в `AUTHOR_ID` полем, а не контекстом).

**Требует проверки:** достижимость `assignedById` из пользовательского ввода и корректность
`author/responsible` в записях, созданных веб-формами.
