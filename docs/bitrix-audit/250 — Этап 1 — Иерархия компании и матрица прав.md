# Этап 1 — Иерархия компании и матрица прав
### Аудит: `intranet`, `humanresources`, `main` (Access), `crm/lib/security`

> Источник: распакованная коробка `/home/bitrix/www/bitrix/modules/`. Разобрано чтением реальных
> реализаций (не по названиям классов): DDL из `install/migrations/tables.php`, репозитории, генераторы

## 1. Архитектурный разбор и Поток данных (Data Flow)

### 1.1. Три конкурирующих модели оргструктуры в одной коробке

Коробка содержит **три несводимые модели** организационной структуры плюс адаптер-переводчик между ними.
Это главный архитектурный факт всего этапа.

| Слой | Где живёт | Представление дерева | Статус |
|---|---|---|---|
| **A. ИБ-секции (легаси)** | `iblock`: секции инфоблока `intranet.iblock_structure`, `LEFT_MARGIN/RIGHT_MARGIN` (nested sets), `UF_HEAD` как user-field секции | nested sets + adjacency (`IBLOCK_SECTION_ID`) | deprecated, но код активен |
| **B. HumanResources (новый)** | модуль `humanresources`: `b_hr_structure*` | adjacency (`PARENT_ID`) + **closure table** `b_hr_structure_node_path` | целевая модель |
| **C. Коды доступа (субъект)** | `b_user_access` (`USER_ID, PROVIDER_ID, ACCESS_CODE`) | плоский список строк-кодов (`U6`, `D12`, `SND7`, `G5`, `AD3`…) | активен, ядро прав |
| **Adapter** | `humanresources/lib/Compatibility/Adapter/StructureBackwardAdapter.php` | отдаёт старый формат `['TREE'=>…,'DATA'=>…]` поверх слоя B | активен |

**Ключевой файл A** — `/bitrix/modules/intranet/classes/general/utils.php`:


`StructureBackwardAdapter::getStructure()` (строки 29–74) — чистый геттер, который **регистрирует
агентов миграции** (`CAgent::AddAgent(...StructureBackwardConverter...)`) при первом вызове: побочный
эффект внутри операции чтения.

`NodePathTable::recalculate()` (`humanresources/lib/Model/NodePathTable.php`) строит closure-таблицу
**рекурсивным SQL**: на каждой итерации `INNER JOIN` сама на себя `depth+1` раз, `INS​ERT IGNORE`,
максимум 64 глубины, `set_time_limit(0)`. `appendNode()` — одна вставка `SEL​ECT parent, node, depth+1 …`;
`moveWithSubtree()` — два сырых запроса (DELETE лишних путей + INS​ERT новых комбинаций) с
разными ветками для MySQL и PostgreSQL.

Руководитель — **не поле узла**, а роль участника: `NodeMember::DEFAULT_ROLE_XML_ID['HEAD']`
(`MEMBER_HEAD`), см. `crm/lib/integration/humanresources/departmentqueries.php::getUserIdsByDepartmentNodeCollection()`.

### 1.2. Субъектные коды доступа — единая валюта прав

`main/lib/Access/AccessCode.php` — парсер и словарь всех префиксов:

```
U6       пользователь            IU6      intranet-пользователь
D12      отдел iblock            DR12     отдел + все подотделы
SND7     отдел HR                SNDR7    отдел HR + подотделы
SNT3     команда HR              SNTR3    команда HR + подчинённые
G5       группа                  AD3/AE3/AT3  руководитель/сотрудник/заместитель

```

Коды материализуются в `b_user_access` классом `CAccess` (`main/classes/general/access.php`,
`UpdateCodes()`/`GetUserCodes()`), считаются **лениво, по провайдеру**, с кэшем «нужно ли пересчитывать»
(`NeedToRecalculate`, cache dir `access_check`).

Коды — это мост между оргструктурой и правами: **роль привязана не к пользователю, а к коду**.

### 1.3. Матрица прав CRM — схема и таблицы

DDL (`crm/install/migrations/tables.php:355–388`):

```sql
b_crm_role          (ID, NAME, IS_SYSTEM, CODE, GROUP_CODE)            + IX(GROUP_CODE)
b_crm_role_relation (ID, ROLE_ID, RELATION)  -- RELATION = access code ('U6','SND7','G5')
b_crm_role_perms    (ID, ROLE_ID, ENTITY(20), FIELD(30), FIELD_VALUE(255),
                     PERM_TYPE(20), ATTR(1), SETTINGS TEXT)             -- EAV-матрица прав
                     + IX (ROLE_ID,PERM_TYPE,ENTITY), IX (ENTITY,PERM_TYPE,ATTR)
```

`ATTR` — уровень доступа, ровно один байт (`char(1)`), значения объявлены в `crm/include.php:9–15`:

| Константа | Байт | Смысл |
|---|---|---|
| `BX_CRM_PERM_NONE` | `''` | запрещено |
| `BX_CRM_PERM_SELF` | `A` | только свои |
| `BX_CRM_PERM_DEPARTMENT` | `D` | свой отдел |
| `BX_CRM_PERM_SUBDEPARTMENT` | `F` | свой отдел и подотделы |
| `BX_CRM_PERM_OPEN` | `O` | все «открытые» |
| `BX_CRM_PERM_ALL` | `X` | всё |
| `BX_CRM_PERM_CONFIG` | `C` | настройки/роли |

Слияние ролей — `max($attribute)` (**сравнение строк**, `PermissionLevel::addValueAttribute()`), т.е.
упорядоченность уровней обеспечивается ASCII-порядком букв: `'' < A < C < D < F < O < X`. Тот же трюк
в `CMain::GetUserRight()` (`$permission['G_ACCESS'] > $right`). Работает, пока алфавит однобуквенный и
монотонный; добавление двухбуквенного уровня молча ломает семантику.

`FIELD`+`FIELD_VALUE` — **ограничение на конкретное поле**, чаще всего `STAGE_IDC3:NEW` (этап воронки),
`SETTINGS` — JSON для нового типа разрешений (preset «свой отдел + открытые»).

Пример строки: `(ROLE_ID=4, ENTITY='DEAL', FIELD='STAGE_IDC3:PREPAYMENT_INVOICE', FIELD_VALUE='',
PERM_TYPE='READ', ATTR='D')` → «читать сделки категории 3 на этапе PREPAYMENT_INVOICE, если
ответственный из моего отдела».

Таблица-наблюдатель (`b_crm_role_relation`) хранит только коды — разрешение ролей на пользователя:

```
b_user_access (коды пользователя)  --RELATION IN-->  b_crm_role_relation.ROLE_ID
                                                   -> b_crm_role_perms -> PermissionLevel
```

### 1.4. Материализованный ACL-индекс (самая важная находка этапа)

На каждую CRM-сущность — **своя таблица доступа** (`crm/lib/security/accessattribute/manager.php`
динамически компилирует ORM-сущность `b_crm_access_attr_<entity>`):

```sql
b_crm_access_attr_deal (
  ID BIGINT PK,
  ENTITY_ID   INT NOT NULL,   -- id сделки
  CATEGORY_ID INT NOT NULL,   -- воронка
  USER_ID     INT NOT NULL,   -- ответственный (ASSIGNED_BY_ID)
  IS_OPENED   CHAR(1),        -- «открытая» сущность
  IS_ALWAYS_READABLE CHAR(1),
  PROGRESS_STEP VARCHAR(50)   -- этап, '' если не применимо
  + UNIQUE (ENTITY_ID, USER_ID, IS_OPENED, IS_ALWAYS_READABLE, PROGRESS_STEP)
  + 9 индексов: (USER_ID,ENTITY_ID) (IS_OPENED,ENTITY_ID) (ENTITY_ID,IS_OPENED)
                (IS_ALWAYS_READABLE,ENTITY_ID) (ENTITY_ID,IS_ALWAYS_READABLE)
                (CATEGORY_ID,ENTITY_ID) (ENTITY_ID,CATEGORY_ID,USER_ID)
                (CATEGORY_ID,USER_ID,ENTITY_ID)
)   -- продублировано для lead/deal/contact/company/quote/order
```

Строки пишутся при сохранении сущности: `Service\Operation::updatePermissions()`
(`crm/lib/Service/Operation.php:1207–1242`) → `Controller::register()` →
`EntityAccessAttributeTable::upsert()` (SEL​ECT COUNT → UPDATE или INSERT, без транзакции).

Три варианта выхлопа (`crm/lib/security/querybuilder/result/`):

* `JoinResult::make()` → `INNER JOIN b_crm_access_attr_deal P ON D.ID = P.ENTITY_ID AND (…)`;

с числом отделов и ролей — только длина IN-списков.

## 2. Удачные решения (What to Keep / Patterns to Adopt)

### 2.1. Closure table для оргструктуры — правильно

`b_hr_structure_node_path(PARENT_ID, CHILD_ID, DEPTH)` даёт **константные** ответы без рекурсивного SQL:

```sql
-- все подчинённые отделы (включая себя)
SELECT CHILD_ID, DEPTH FR​OM b_hr_structure_node_path WHERE PARENT_ID = :root;
-- все вышестоящие
SELE​CT PARENT_ID, DEPTH FR​OM b_hr_structure_node_path WH​ERE CHILD_ID = :node;
-- расстояние «начальник ↔ подчинённый» = DEPTH
```

Почему устойчиво: выборка не зависит от глубины и размера дерева, не требует рекурсии в приложении,
поддерживается двумя дешёвыми операциями при вставке (`appendNode` — один `INSERT … SELE​CT`) и
единственным тяжёлым случаем — пересчётом при массовой перестановке (`recalculate`, вынесен в отдельную
операцию с `set_time_limit(0)`).

**Стоит перенести как есть** (см. §5.1), добавив: материализацию путей в один запрос через
`WITH RECURSIVE` вместо `INNER JOIN` в цикле, и партиционирование по `STRUCTURE_ID`.

### 2.2. «Права как данные», а не как подзапросы — главный паттерн коробки

`b_crm_access_attr_*` — это **материализованный индекс доступа**: право на чтение конкретной сделки
представлено одной строкой, которую можно проверить по индексу. Сравнение с классическим
`PermissionSql` (создание сотен JOIN к каждому запросу) — здесь **ровно один JOIN/IN**.

Псевдокод целевой реализации:

```text
on_entity_saved(entity):
    attrs = { owner: entity.responsible_id, opened: entity.opened,
              category: entity.category_id, step: entity.stage_id,
              observers: observers_of(entity.id) }
    upsert acl(entity.id, attrs)          # в одной транзакции с записью сущности

query_list(subject, entity_type, filter, page):
    g = policy.evaluate(subject.roles, entity_type, op=READ)   # → набор условий
    if g == ALL: return query(filter, page)
    if g == NONE: return empty
    sql = query(filter, page) JOIN acl ON acl.entity_id = e.id
                    AND (g.owner IN subject.principals OR g.opened AND acl.is_opened)
                    AND (g.category IN subject.categories) AND (g.step IN subject.steps)
    return sql
```

### 2.3. Роль = таблица строк, а не набор булевых флагов

`b_crm_role_perms` с осями `ENTITY × PERM_TYPE × (FIELD, FIELD_VALUE) × ATTR` — это по сути
**ABAC-политика в реляционном виде**: одна строка = одно правило «кто-то может что-то при условии».
Уровни `ATTR` упорядочены (`max($attribute)` в `PermissionLevel`), поэтому слияние ролей — это `MAX()`,
а не сложная логика объединений. Ограничение по этапу воронки живёт в том же месте, что и ограничение
по отделу — единая модель, отдельные «ветки» кода не нужны.

### 2.4. Субъектные коды доступа как антикоррупционный слой

`U6 / SND7 / G5 / AD3` — единая строка, которой обмениваются оргструктура, группы, HR и CRM.
Роли не знают, откуда пришёл код (`b_crm_role_relation.RELATION`), а значит подмена источника
(iblock → HR) не трогает матрицу прав. Это классический **Access Code как идентичность субъекта**,
и он окупил себя: вся миграция `intranet → humanresources` прошла без переписывания ролей.

### 2.5. Развёртывание иерархии в плоский список на границе запроса

`RestrictionsByAttributes::createEntityRestrictionData()` заменяет `SND7` на конкретные `USER_ID`
до генерации SQL (`DepartmentProvider::getHrDepartmentUsers()` с `md5`-кэшем в памяти запроса):

```php
if (!empty($permissionSet['DEPARTMENT_IDS'])) {
    $restriction['USER_IDS'] = array_unique(array_merge(
        $restriction['USER_IDS'],
        $this->getHrDepartmentUsers($permissionSet['DEPARTMENT_IDS'])
    ));
}
```

Плюс дедупликация условий через `md5`-хэши (`joinPermissionSetsProgressSteps`, `createRestrictionMap`) —
ряды с одинаковыми ограничениями схлопываются в одно условие. Итоговый `WH​ERE` короткий и предсказуемый.

### 2.6. Кэш собранного результата с содержательным ключом

`ItemsList::buildQueryResult()` кэширует не строки, а **построенный объект ограничения** по
`sha256(userId, entityTypes, operations, resultOption, aliasPrefix, …)` (лимит 64, deep-clone на выдаче).
Это убирает повторную работу генератора SQL в рамках запроса и не тащит состояние между запросами.

### 2.7. Управляемая миграция тяжёлых данных агентами

`crm/lib/agent/security/dynamictypes/refilldynamictypeattr.php` — безопасный перенос прав для
смарт-сущностей: курсор по `ID`, чанки (`AttrConvertOptions::getLimit()`), прогресс в `Option`
(`current_id`, `last_id`, `process_ids`), dual-write в обоих контроллерах на время перехода
(`Service\Operation::updatePermissions()`), флаг-переключатель в опциях. **Этот паттерн (курсор +
чанки + переключатель + dual-write + агент доводки) — эталон для любых больших миграций.**

### 2.8. Единая точка входа для списков

`Factory::getItemsFilteredByPermissions()` — единственная дверь, через которую идут все списки,
канбаны, истории, AI-контексты. Внедрение прав не размазано по контроллерам → риск «забыл проверить»
существенно ниже, чем в легаси.

## 3. Антипаттерны и Архитектурные тупики (What NOT to Do)

### 3.1. Три модели оргструктуры + адаптер с побочными эффектами
* `CIntranetUtils::GetStructure()`, `GetSubordinateDepartments()`, `GetDepartmentManager()` помечены
  `@deprecated`, но остаются в коде и по-прежнему **рекурсивно обходят дерево в PHP**:

```php
// utils.php:1682  — полный проход по всем отделам ради одного
foreach (self::$SECTIONS_SETTINGS_WITHOUT_EMPLOYEE_CACHE['DATA'] as $arSection)
    if ($arSection['UF_HEAD'] == $USER_ID) $arSections[] = $arSection['ID'];
if ($bRecursive && !empty($arSections))
    foreach ($arSections as $section_id)
        $arSections = array_merge($arSections, self::GetDeparmentsTree($section_id, true));
```
* `StructureBackwardAdapter::getStructure()` — геттер, который **регистрирует агентов и пишет опции**
  (строки 36–60). Чтение не должно менять состояние.
* Результат адаптера кэшируется на **30 дней** (`CPHPCache`, теги `intranet_department_structure`) —
  структура «замерзает» между инвалидациями.

**Вывод:** никогда не держите две способные разойтись модели дерева и «переводчик» между ними на
горячем пути. Одна модель + read-model под конкретный сценарий.
