### 4.3. Двухфазный фетч и точки обхода прав
* `Factory::getItems()` **не применяет права сам** — права появляются только если вызывающий выбрал
  `getItemsFilteredByPermissions()`. Прямой `getItems(['filter'=>…])` возвращает всё.
  Защита — исключительно соглашение; поиск по коду показывает оба варианта использования.
* `unset($params['runtime']['permissions'])` во второй фазе (`Factory.php:446`) — скрытое снятие
  ограничения; корректно только в предположении, что фаза 1 уже фильтровала. Если `isSkipSelectIdsHack()`
  вернул true (строгий фильтр по `ID`), фильтрация прав **не выполняется вовсе** — безопасно только
  потому, что `=ID` приходит от вызывающего с уже проверенным идентификатором.

### 4.4. Доступность `disableAllChecks()` из разных контуров
`disableAllChecks()` отключает сразу и доступ, и валидацию полей, и лимиты. Используется в
AI-инструментах (`aiassistant/tools/...`) и интеграциях. Если любой из этих путей принимает
пользовательские параметры (имя поля, значение), это комбинация «вне валидации + вне прав».
Нужна проверка: где валидируются `fieldName/value` в `basesetfieldvaluetool.php` и
`userfieldhelper.php:130`.

### 4.5. Гонки и отсутствие атомарности
* Пайплайн без транзакции (классический путь): `save()` прошёл → `updatePermissions()` упал →
  сущность без ACL-строки = **не видна никому** (fail-closed, «пропавшая» запись); либо
  `updateSearchIndexes()` упал → запись не ищется.
* `TypeTable::onBeforeAdd` делает `dropTable()` незавершённого типа, а `onAfterAdd` — серию DDL;
  параллельное создание двух типов с одинаковым `ENTITY_TYPE_ID` ловится только
  `UNIQUE(ENTITY_TYPE_ID)` и `isCreatingInProgress(30 sec)`.
* `StatusTable` инвариант «одна успешная стадия» проверяется SELECT-ом в `onBeforeAdd` —
  **TOCTOU**: два параллельных запроса добавят две стадии `S`.

### 4.6. Что проверено и что нет
Подтверждено чтением кода: пайплайн операций, отсутствие транзакции на классическом пути,
места `disableCheckAccess/disableAllChecks`, контекст `setUserId(... ?: 1)`, схемы таблиц,
индексы, DDL в рантайме, баг `ResolveSuspended` для `SmartB2eDocument`.
**Не проверено экспериментом:** достижимость цепочек §4.1–4.4 из внешнего HTTP (нужен сценарный
тест веб-формы и REST), реальные планы запросов с 22 индексами, поведение `clone $item` при
глубоких коллекциях, фактические последствия `unset(runtime.permissions)` при
`isSkipSelectIdsHack()`.

## 5. Спецификация для Новой CRM (Target Architecture)

### 5.1. Схема базы данных: ядро сущностей

Принцип: **одна таблица на семантически разные сущности не нужна** — единая оболочка
(`entity_type` + JSONB атрибутов) + типизированные колонки под горячие поля + отдельные таблицы
на связи и активности.

```sql
CREATE TYPE entity_state AS ENUM ('active','deleted');

-- ============ ЕДИНЫЙ КОНТУР СУЩНОСТЕЙ ============
CREATE TABLE crm_entity (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    entity_type  TEXT   NOT NULL,              -- 'deal','lead','contact','smart:128'
    external_id  TEXT,
    state        entity_state NOT NULL DEFAULT 'active',
    deleted_at   TIMESTAMPTZ,                  -- корзина = состояние, а не отдельный тип
    title        TEXT,
    responsible_id BIGINT NOT NULL,
    owner_ids    BIGINT[] NOT NULL DEFAULT '{}',  -- участники/наблюдатели (denormalized для прав)
    is_opened    BOOLEAN NOT NULL DEFAULT FALSE,
    category_id  BIGINT,                       -- воронка (NULL где нет)
    stage_id     TEXT,                         -- 'C5:PREPAYMENT' | 'NEW'
    stage_semantic CHAR(1) CHECK (stage_semantic IN ('P','S','F')),
    begindate DATE, closedate DATE,
    opportunity  NUMERIC(18,4), currency CHAR(3),
    attrs        JSONB NOT NULL DEFAULT '{}',  -- все остальные поля (в т.ч. пользовательские)
    search_document TSVECTOR,
    created_by BIGINT NOT NULL, updated_by BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_activity_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT crm_entity_stage_semantic_check
        CHECK (stage_semantic IS NULL OR stage_id IS NOT NULL)
);
-- триггер/код: не более одной 'S' на (entity_type, category_id) обеспечивается
-- частичным уникальным индексом успешного этапа в справочнике stage, а не проверкой в приложении

CREATE INDEX crm_entity_live_idx ON crm_entity (entity_type, state, stage_id, responsible_id)
    WHERE state = 'active';
CREATE INDEX crm_entity_owner_idx ON crm_entity (responsible_id) WHERE state='active';
CREATE INDEX crm_entity_open_idx  ON crm_entity (entity_type, is_opened) WHERE state='active';
CREATE INDEX crm_entity_stage_sem_idx ON crm_entity (entity_type, stage_semantic, category_id);
CREATE INDEX crm_entity_activity_idx ON crm_entity (last_activity_at DESC);
CREATE INDEX crm_entity_attrs_gin ON crm_entity USING GIN (attrs jsonb_path_ops);
CREATE INDEX crm_entity_search_idx ON crm_entity USING GIN (search_document);

-- пользовательские поля: метаданные отдельно, значения в JSONB (+ матер. колонка под индекс)
CREATE TABLE crm_field (
    id BIGINT PRIMARY KEY, entity_type TEXT NOT NULL, code TEXT NOT NULL,
    type TEXT NOT NULL,               -- 'string','date','enum','money','file','reference'
    settings JSONB NOT NULL DEFAULT '{}',
    is_mandatory BOOLEAN DEFAULT FALSE,
    sort INT DEFAULT 0, is_active BOOLEAN DEFAULT TRUE,
    UNIQUE (entity_type, code)
);
-- индексируемые пользовательские поля объявляются как expression index по attrs:
--   CREATE INDEX ON crm_entity ((attrs->>'deadline')) WHERE state='active';
-- и маппятся в реестр полей на старте приложения (никакого runtime DDL)

-- ============ ВОРОНКИ / СТАДИИ ============
CREATE TABLE crm_category (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    entity_type TEXT NOT NULL, code TEXT, name TEXT NOT NULL,
    is_default BOOLEAN NOT NULL DEFAULT FALSE, sort INT NOT NULL DEFAULT 0,
    settings JSONB NOT NULL DEFAULT '{}',
    UNIQUE (entity_type, code)
);
CREATE TABLE crm_stage (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category_id BIGINT NOT NULL REFERENCES crm_category(id) ON DELETE CASCADE,
    code TEXT NOT NULL,               -- 'PREPAYMENT' (без дублирования категории в коде!)
    name TEXT NOT NULL, sort INT NOT NULL,
    semantic CHAR(1) CHECK (semantic IN ('P','S','F')),
    color TEXT,
    UNIQUE (category_id, code)
);
-- ровно одна стадия успеха на воронку:
CREATE UNIQUE INDEX crm_stage_one_success
    ON crm_stage (category_id) WHERE semantic = 'S';

-- ============ АКТИВНОСТИ / ТАЙМЛАЙН ============
CREATE TABLE crm_activity (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind TEXT NOT NULL,               -- 'call','email','task','note','system'
    direction SMALLINT, subject TEXT, body TEXT, body_format TEXT,
    responsible_id BIGINT NOT NULL, author_id BIGINT,
    deadline TIMESTAMPTZ, status TEXT,
    provider TEXT, provider_ref TEXT,
    storage JSONB NOT NULL DEFAULT '{}',   -- вложения/записи звонков
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);
-- партиции помесячно; FK на сущность — в crm_activity_binding, чтобы не ломать партиционирование

CREATE TABLE crm_activity_binding (
    activity_id BIGINT NOT NULL,
    entity_type TEXT NOT NULL, entity_id BIGINT NOT NULL,
    is_fixed BOOLEAN NOT NULL DEFAULT FALSE,
    PRIMARY KEY (activity_id, entity_type, entity_id)
);
CREATE INDEX crm_activity_binding_entity_idx ON crm_activity_binding (entity_type, entity_id);

CREATE TABLE crm_timeline (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind TEXT NOT NULL,               -- ссылка на тип события (реестр, не if/elseif)
    entity_type TEXT NOT NULL, entity_id BIGINT NOT NULL,
    author_id BIGINT, payload JSONB NOT NULL DEFAULT '{}',
    source_key TEXT,                  -- идемпотентность: UNIQUE(source_key) где не null
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);
CREATE UNIQUE INDEX crm_timeline_source_uq ON crm_timeline (source_key) WHERE source_key IS NOT NULL;
CREATE INDEX crm_timeline_entity_idx ON crm_timeline (entity_type, entity_id, created_at DESC);
CREATE INDEX crm_timeline_fts_idx ON crm_timeline USING GIN (to_tsvector('simple', payload->>'text'));
```

### 5.2. Архитектура сервисов (Hexagonal)

```
┌ api-gateway ─────────────────────────────────────────────────┐
│  REST /v1/*   ·  gRPC internal  ·  WS events                 │
└───────────────┬──────────────────────────────────────────────┘
                │
   ┌────────────▼─────────────  application layer  ────────────────┐
   │  CommandBus: CreateDeal, SetStage, AssignOwner, AddActivity   │
   │  QueryBus : ListDeals (query), GetTimeline (query)            │
   │  каждый Command = один объект с invariants + одна транзакция  │
   └───┬───────────────┬───────────────┬──────────────┬────────────┘
       │               │               │              │
  ┌────▼────┐   ┌──────▼──────┐  ┌─────▼─────┐  ┌─────▼──────┐
  │entity   │   │policy       │  │stage      │  │timeline    │  domain services
  │service  │   │service      │  │service    │  │service     │
  └────┬────┘   └──────┬──────┘  └─────┬─────┘  └─────┬──────┘
       │               │               │              │
  ┌────▼───────────────▼───────────────▼──────────────▼──────┐  ports
  │  EntityRepository · PolicyDecisionPoint · StageRepo       │
  │  ActivityRepository · TimelineRepository · OutboxRepo     │
  └───────────────────────┬──────────────────────────────────┘
                          │  adapters
  ┌───────────────────────▼──────────────────────────────────┐
  │ PostgreSQL (первичное хранилище) + outbox                 │
  │ Redis (кэш решений политики, сессии, pub/sub инвалидации) │
  │ Search: OpenSearch/PG FTS (поисковые индексы)             │
  │ Kafka/Redpanda: события (entity.*, policy.*, membership.*)│
  └──────────────────────────────────────────────────────────┘
```

Ключевое отличие от Bitrix: **Command — единственное место, где меняются данные**.
`Item::save()` «из любого места» невозможен: репозиторий публичен только для application-слоя
(внешний код получает read-model и команды).

### 5.3. Схема фоновых воркеров

| Воркер | Технология | Задача |
|---|---|---|
| `outbox-relay` | Go, `SELECT … FOR UPDATE SKIP LOCKED` → Kafka | гарантированная доставка событий после COMMIT |
| `search-indexer` | Kafka consumer | `entity.updated` → индекс полнотекста/фильтров |
| `acl-projector` | Kafka consumer | `entity.updated/membership.changed` → пересчёт `acl_item` (этап 1, §5.3) |
| `timeline-denorm` | Kafka consumer | пересчёт `search_document`, счётчиков активностей |
| `stage-transition-auditor` | pg_cron + Waterline | контроль инварианта «одна S-стадия», сверка `stage_semantic` со справочником |
| `recycle-bin-janitor` | Temporal workflow | отложенные удаления (`deleted_at` старше N дней → каскадная чистка связей) |
| `dedupe-scanner` | периодическая job | фоновая дедупликация контактов/компаний (паттерн `crm/integrity`) |
| `field-registry-sync` | миграции/CI | изменения `crm_field` → codegen индексов, API-схем, фильтров |

Принцип: **никакого DDL из веб-запроса**. Добавление поля = запись в `crm_field` + (при необходимости)
выраженческий индекс, создаваемый управляемой миграцией; создание сущности-типа = запись каталога +
регистрация в реестре обработчиков.

### 5.4. Контракты API

```yaml

{type:"timeline.item_added", entity:{type,id}, item:{...}}
```

### 5.6. Чек-лист этапа 2

1. Один вход на запись (Command), одна транзакция, side-effects только после COMMIT.
2. Права — обязательный интерсептор репозитория, отключение только явной системной ролью.
3. Поля описываются декларативно (как в `getFieldsSettings`) и валидируются в одном месте.
4. Стадии — справочник с FK и частичным уникальным индексом «одна успешная» в самой БД.
5. Идентичность сущности — строка; удаление — состояние; никаких +17/+64/паритетов.
6. Никакого DDL из рантайма; типизационные изменения — через миграции и каталог.
7. Таймлайн — append-only партиции + идемпотентный `source_key` + батчинг отрисовки.
8. Индексов — столько, сколько подтверждено `pg_stat_statements`; каждый новый — с обоснованием.
