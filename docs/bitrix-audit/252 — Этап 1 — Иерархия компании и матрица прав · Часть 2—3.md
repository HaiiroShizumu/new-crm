### 3.2. Вся структура в памяти процесса
`UserSubordinate::getStructure()` и `UserSubordinate::$cache` — статические массивы `DATA` со всеми
отделами и списком `EMPLOYEES` в каждом узле. На портале с тысячами сотрудников это:
(а) дорогой прогрев, (б) O(N) обходы на каждый `getSubordinate()`, (в) N+1 по `UF_HEAD`,
(г) раздувание PHP-FPM RSS на каждый воркер. Правильное решение — один запрос к closure-таблице.

### 3.3. Materialized ACL, у которого «дубль на каждый тип»
Шесть почти идентичных таблиц `b_crm_access_attr_{lead,deal,contact,company,quote,order}` с копипастой
9 индексов каждая. Динамическая компиляция ORM-сущности под тип (`AccessAttribute\Manager::compileEntity`)
удобна разработчику, но:
* планы запросов и статистика по индексам дробятся на 6+ копий;
* миграция схемы = 6 однотипных миграций;
* добавление смарт-сущности — ещё одна таблица с теми же 9 индексами.

Одна таблица с `entity_type_id` + частичными индексами решает это без потери производительности.

### 3.4. Побочные эффекты в read-пути
```php
// attributesprovider.php::loadUserAccessCodes()
$access = new \CAccess();
$access->UpdateCodes(['USER_ID' => $userId]);   // ЗАПИСЬ в БД внутри чтения прав
```
Плюс `StructureBackwardAdapter::getStructure()` регистрирует агентов (см. 3.1).
Чтение прав не должно ни писать в БД, ни планировать задачи: это ломает read-only реплики,
усиливает лок и превращает запрос в «сюрприз» с side-effect'ами.

### 3.5. Порядко-зависимая мемоизация с fail-closed исходом
`PermissionsManager::load()` (`role/permissionsmanager.php`):

```php
if (isset($this->loadedEntities['byEntity'][$entity])
    || isset($this->loadedEntities['byPermission'][$permissionType])) {
    return $this->loadedEntities['data'][$resultKey] ?? $this->createPermissionLevel(...); // ПУСТОЙ объект
}
if ($permissionType === UserPermissions::OPERATION_READ) {
    $filter['=PERM_TYPE'] = $permissionType;      // читаем ВСЕ сущности сразу
    $this->loadedEntities['byPermission'][$permissionType] = true;
} else {
    $filter['=ENTITY'] = $entity;                 // читаем ВСЕ типы прав одной сущности
    $this->loadedEntities['byEntity'][$entity] = true;
}
```

Фильтры для «READ» и «не-READ» **асимметричны**, а флаги кэша ставятся в обоих случаях. Следствие:

1. первый вызов `load(DEAL, READ)` → загружены все строки `PERM_TYPE='READ'`, флаг `byPermission['READ']`;
2. следующий вызов `load(CONTACT, WRITE)` → срабатывает guard → `data['CONTACT_WRITE']` отсутствует →
   возвращается **пустой** `PermissionLevel`;
3. `PermissionLevel::hasPermission()`: `empty($this->maxAttribute)` → `false` → **доступ запрещён**.

То есть результат проверки зависит от того, была ли раньше в этом же PHP-процессе проверка другого
типа/сущности. Это fail-closed (безопаснее, чем fail-open), но это **недетерминированное поведение**,
которое лечится только перезапросом процесса — типичный источник «не воспроизводится у меня».
Кэш обязан быть безусловно полным: ключ `(entity, permType)` и явный флаг «этот ключ загружен».

### 3.6. Валидация, которая валидирует один элемент
```php
protected function validatePermissions(array $permissions): bool
{
    foreach ($permissions as $id => $value) {
        return PermissionDictionary::recursiveValidatePermission($permissions, $id); // return!
    }
    return true;
}
```
(`main/lib/Access/Role/RoleUtil.php`) — `return` вместо `continue`/накопления: проверяется **только
первый** элемент массива. Плюс сама проверка сверяет словарь не с `PermissionDictionary`, а с тем же
переданным массивом, поэтому произвольный `PERMISSION_ID` проходит валидацию для односегментных id.

### 3.7. Сырой SQL вместо ORM там, где это не оправдано
* `NodePathTable::recalculate()/moveWithSubtree()/deleteListByStructureId()` — `INS​ERT IGNORE`,
  ручные ветки `mysql`/`pgsql`, `DELETE $table FR​OM $table JOIN …`, `set_time_limit(0)`.
* `RoleUtil::updatePermissions()/updateRoleRelations()` — `deleteList` + ручной `INS​ERT … VALUES`
  через `SqlExpression`, минуя `checkFields`/валидацию таблицы.
* `RolePermissionTable::removePermissions()` — ручной `DELETE … WHERE` + предварительный `SEL​ECT`
  (проверка-then-действие) и `cleanCache()` **до** выполнения удаления.
* `NodeMemberRepository::getCommonUsersFromRelation()`:

```php
$users = implode(', ', $usersToCompare);   // int[] по типу, но без приведения
...
WHERE nm.ENTITY_ID IN ($users)
```
Конкатенация вместо параметризации: спасает только то, что источник — `int[]` по договорённости.

### 3.8. Non-atomic «пересборка прав»
```php
public static function appendPermissions(int $roleId, array $permissionModels): void
{
    self::removePermissions($roleId, $permissionModels);   // точечные DELETE
    foreach ($permissionModels as $model) {
        RolePermissionTable::add([...]);                   // INS​ERT по одному, без транзакции
    }
}
```
И `RoleRelationTable::updateForRole()` = `deleteAllForRole()` + вставки. Если процесс упадёт на середине
или параллельный запрос прочитает состояние между DELETE и INS​ERT — роль окажется **без прав**.
Нужен `DELETE + COPY/INS​ERT` в одной транзакции (или `INS​ERT … ON CONFLICT` + diff-удаление).

### 3.9. Битые обработчики событий
```php
// crm/lib/security/role/model/roletable.php:129
$fields = $event->getParameters()['fields'] ?? [];
$fields['ID'] = $id['ID'];     // $id не определён в этой ветке
```
Работает только пока логирование выключено (`RolePermissionLogContext::isOrmEventsLogEnabled()`), т.е.
ошибка «всплывёт» в момент включения диагностики — худшее место и время.

### 3.10. Утечка абстракций и «контроллер-конверт»
* `CCrmPerms` — легаси-класс, всячески помеченный `@deprecated`, но по-прежнему является точкой входа
  для поиска, livefeed, activity (`BuildSqlForEntitySet`), т.е. два стека прав живут одновременно.
* `Security\Controller\Compatible` — «должен быть последним» в реестре и умеет смешивать intranet- и
  HR-коды (`attributesprovider.php`: `SUBINTRANET` подмешивается только если `Compatible::isAvailable()`).
* Опции-флаги прямо в построителе условий:
  `Option::get('crm','CRM_MOVE_OBSERVERS_TO_ACCESS_ATTR_IN_WORK','Y') === 'Y'` (`ConditionBuilder`),
  `AttrConvertOptions::isEntityTypeNotConvertedYet()` в `Manager::resolveController()`.
  Флаги миграции в горячем пути прав — это невоспроизводимость поведения между инсталляциями.

### 3.11. Глобальное состояние и `global`
`CMain::GetUserRight()` начинается с `global $USER`, дальше `COption::GetOptionString`, затем сравнение
строк прав `>` (лексикографический максимум уровней). Тот же паттерн в `CIntranetUtils`
(`global $USER`, `global $CACHE_MANAGER, $DB`). Всё это делает тестирование и переиспользование
кода за пределами веб-запроса крайне затруднительным.

### 3.12. 9 индексов на таблицу ACL, включая взаимоисключающие
`(IS_OPENED, ENTITY_ID)` и `(ENTITY_ID, IS_OPENED)`, `(CATEGORY_ID, USER_ID, ENTITY_ID)` и
`(ENTITY_ID, CATEGORY_ID, USER_ID)` — это индексы, покрытые другими индексами в обратном порядке частично
и размывающие write-amplification: каждая вставка/обновление сущности дороже в 9 раз.

## 4. Анализ безопасности и Уязвимостей (Security Audit)

### 4.1. IDOR и проверка прав на выборке
Одиночная проверка (`UserPermissions::item()->canRead()`) идёт по атрибутам сущности и матрице ролей —
архитектурно корректно, «дыр» вида `ID` из запроса без проверки не найдено на разобранных путях.

Однако список всегда строится **вручную**: `ItemsList::applyAvailableItems*` нужно вызвать явно.
Все найденные места вызова — централизованные (`Factory`, kanban, history, AI), но любой новый код,
написавший `DataManager::getList()` напрямую, **обходит права молча**. Это главный системный риск:
отсутствие принудительного guard'а на уровне доступа к данным.

**Рекомендация для новой системы:** права применяются в репозитории/интерсепторе, а не в вызывающем
коде; «пропустить» невозможно по умолчанию (опция `SELECT` без policy = миграция со звёздочкой).

### 4.2. Потенциальная SQL-инъекция в каскадном обновлении прав
```php
// main/lib/Access/Permission/AccessPermissionTable.php::updateChildPermission()
$sql = "
    UPDATE ". $helper->quote(static::getTableName()) ."
    SET VAL​UE = 0
    WHERE ROLE_ID = ". $data['ROLE_ID'] ."
      AND PERMISSION_ID LIKE '". $data['PERMISSION_ID'] .".%' ";
```
`PERMISSION_ID` вставляется в литерал **без экранирования**. `ROLE_ID` приводится к int в
`loadUpdateRow` только при частичном `$data` (иначе берётся из `$data` как есть).
Путь записи: `RoleUtil::updatePermissions()` идёт сырым `INSERT` (в обход ORM), но таблица
поддерживает и ORM-путь `add()/update()`, где этот хук срабатывает. Статус: **латентная уязвимость**,
зависит от того, кто из фич-кодов/REST вызывает `AccessPermissionTable::add()` с внешним `PERMISSION_ID`.

Проверка обязательна; фикс тривиален: экранировать значение (`$helper->forSql()`) или перейти на
параметризованный `UPDATE … WHERE PERMISSION_ID = ? OR PERMISSION_ID LIKE ?`.

### 4.3. Слабая валидация идентификаторов прав
`RoleUtil::validatePermissions()` (см. 3.6) валидирует первый элемент и сверяет словарь самим массивом.
Итог: в `b_crm_role_perms`/`b_hr_access_permission` можно записать произвольный `PERMISSION_ID`.
Сегодня это ведёт в лучшем случае к неверному разрешению, в худшем — к §4.2.

### 4.4. Гонки и отказы материализации прав
`EntityAccessAttributeTable::upsert()`:

```php
$result = self::getList(['filter'=>['=ENTITY_ID'=>$id], 'sele​ct'=>['CNT'=>COUNT(1),'ID'=>MAX(ID)]])->fetch();
if ($entityCount > 1) { delete; add; }
elseif ($entityCount === 1) { update; } else { add; }
```
* не в транзакции с записью сущности → при падении после `save()` сущность **не видна никому**
  (fail-closed, но это «пропавшие данные» для пользователя); при падении `unregister` — остаётся
  устаревшая строка ACL (fail-**open**: доступ по старому ответственному);
* два параллельных запроса могут оба увидеть `CNT=0` → двойной `INSERT` → нарушение `UNIQUE IX_ACC_ATTR_*_1`
  → исключение в пост-обработке сохранения;
* `deleteByEntity()` — `DELETE FR​OM … WHERE ENTITY_ID = N` сырым SQL с кастом в int (инъекции нет,
  но события ORM (`onAfterDelete`) при этом **не срабатывают** → зависимые кэши не инвалидируются.

### 4.5. Отсутствие внешних ключей
Ни в `b_crm_access_attr_*`, ни в `b_hr_structure_node*`, ни в `b_crm_role*` FK нет. Каскады делаются
руками (`NodePathTable::deleteListByStructureId`, `NodeTable::onAfterDelete`). Любой пропущенный
обработчик = осиротевшая строка. Для ACL осиротевшая строка — это **лишний доступ** (fail-open);
для closure-таблицы — некорректная иерархия.

### 4.6. TTL кэшей прав
```php
private const CACHE_TIME = 8640000; // 100 дней  — AttributesProvider::getRawUserAccessCodes()
private const CACHE_TIME = 8640000; // 100 дней  — PermissionsManager::getUserRoles()
```
Отзыв роли/смена отдела опирается на теговую инвалидацию (`cleanCache()`), а не на срок жизни.
Если тег не очищен (различные кодовые пути: `RoleRelationTable::updateForRole()` чистит теги таблицы,
но `b_user_access` пересчитывается лениво `CAccess::UpdateCodes()`), пользователь сохраняет роли
**до ста дней**. Для прав это недопустимо: TTL должен быть коротким (минуты) + явная invalidation
по событию `role.updated` / `membership.changed`, и обязательно — аудит-лог.

### 4.7. Бессрочные подписанные токены
`crm/lib/security/permissiontoken.php`:

```php
private const SALT = 'permission_token.';
$signer = new Signer();                       // подпись на секрете инсталляции + 'permission_token.<type>'
return $signer->sign(base64_encode(Json::encode($payload)), $this->getSalt($accessTypeCode));
```
Подпись криптографически корректна, но в payload **нет `exp`, `jti`, `nonce`**. Токен
`edit_my_company_requisite` живёт «вечно»: утечка ссылки/HTML = бессрочное право. Токен
`view_activity` дополнительно не привязан к сессии/пользователю-инициатору (проверяется только
наличие relation в чате). Фикс: `exp ≤ 5 мин` + одноразовый `jti` + привязка к сессии.

### 4.8. Обход проверки прав администратором
`QueryBuilder::build()` первым делом: `if ($this->userPermissions->isAdmin()) { setSql(''); return; }`.
Это нормально, но **admin-обход размазан** по всему коду (`PermissionsManager::isAdmin()` в каждом
методе, `CCrmPerms::IsAdmin`, `CMain::GetUserRight` → `W`). В новой системе admin должен быть
`subject.role = system_admin` в едином policy-движке, чтобы исключение было проверяемым и одиноким.

### 4.9. Что проверено и что нет
Подтверждено чтением кода: схемы, генератор SQL, пути проверки, TTL, отсутствие транзакций, raw-SQL
фрагменты. **Не проверялось экспериментом:** реальные планы запросов на объёмных данных, фактическое
поведение кэшей при отзыве прав, воспроизводимость §3.5 на живой инсталляции, достижимость §4.2 через
REST/UI. Это обязательные пункты верификации перед тем, как ссылаться на находки как на доказанные.

## 5. Спецификация для Новой CRM (Target Architecture)

Стек: **Go (или NestJS) + PostgreSQL 16 + Redis**, по модели Hexagonal (ports & adapters).

### 5.1. Схема базы данных: оргструктура

Единая модель дерева (принцип 2.1) + таблицы членства и ролей внутри узла.

```sql
-- ============ ORG (org_service) ============
CREATE TYPE node_type AS ENUM ('COMPANY','DEPARTMENT','TEAM','POSITION');

CREATE TABLE org_structure (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code        TEXT NOT NULL UNIQUE,
    name        TEXT NOT NULL,
    kind        TEXT NOT NULL DEFAULT 'DEFAULT',
    created_by  BIGINT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE org_node (
    id           BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    structure_id BIGINT NOT NULL REFERENCES org_structure(id) ON DELETE CASCADE,
    parent_id    BIGINT REFERENCES org_node(id),      -- adjacency: источник истины
    type         node_type NOT NULL,
    name         TEXT NOT NULL,
    xml_id       TEXT,
    is_active    BOOLEAN NOT NULL DEFAULT TRUE,
    sort         INT NOT NULL DEFAULT 0,
    head_user_id BIGINT,                              -- денормализовано для read-path
    path         LTREE,                               -- PostgreSQL: материализованный путь
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX org_node_path_idx   ON org_node USING GIST (path);
CREATE INDEX org_node_parent_idx ON org_node (structure_id, parent_id);
CREATE INDEX org_node_head_idx   ON org_node (head_user_id) WHERE head_user_id IS NOT NULL;

-- closure (для константных ответов «все подчинённые с глубиной», как в Bitrix)
CREATE TABLE org_node_closure (
    parent_id BIGINT NOT NULL REFERENCES org_node(id) ON DELETE CASCADE,
    child_id  BIGINT NOT NULL REFERENCES org_node(id) ON DELETE CASCADE,
    depth     INT    NOT NULL,
    PRIMARY KEY (parent_id, child_id)
);
CREATE INDEX org_node_closure_child_idx ON org_node_closure (child_id);

-- обновление замыкания (одна операция, без цикла по глубинам)
CREATE OR REPLACE FUNCTION org_subtree(p_id BIGINT) RETURNS SETOF BIGINT LANGUAGE sql STABLE AS $$
    WITH RECURSIVE t AS (
        SELE​CT id FROM org_node WHERE id = p_id
        UNION ALL
        SELE​CT n.id FROM org_node n JOIN t ON n.parent_id = t.id
    ) SELE​CT id FROM t;
$$;

CREATE TABLE org_member (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    node_id   BIGINT NOT NULL REFERENCES org_node(id) ON DELETE CASCADE,
    user_id   BIGINT NOT NULL,
    role      TEXT   NOT NULL,        -- 'HEAD' | 'DEPUTY' | 'EMPLOYEE' | 'HR'
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (node_id, user_id, role)
);
CREATE INDEX org_member_user_idx ON org_member (user_id) WHERE is_active;

-- «кто чей начальник» — одним запросом, без PHP-рекурсии
CREATE VIEW org_reporting_chain AS
SELE​CT c.child_id AS subordinate_id, c.parent_id AS manager_node_id,
       n.head_user_id AS manager_user_id, c.depth
FROM org_node_closure c JOIN org_node n ON n.id = c.parent_id
WH​ERE n.head_user_id IS NOT NULL;
```

`ltree` + `org_node_closure` вместе: `ltree` покрывает «путь/фильтр по префиксу», closure — «глубина и
все вышестоящие». Если нужен один механизм — достаточно `ltree` (`path @> '1.4.9'`), closure добавляется
только при измеренных проблемах производительности.
